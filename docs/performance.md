## 1. 四个问题的答案

| 问题 | 答案（本机，见 §2 规格） | 依据 |
|---|---|---|
| 1. 单机稳定支撑多少事件/秒？瓶颈在哪类资源？ | **约 300–350 events/s**（p99 < 500ms，2KB payload，全部角色同一个 JVM + Docker 里的 MySQL）。瓶颈不是 CPU、不是 GC、不是连接池，而是**每个 ingest 一个 MySQL 事务（≈7 条语句 + 1 次 fsync 提交）**。把 `innodb_flush_log_at_trx_commit` 从 1 改为 2，p50 −25%、p99 −39% | §5、§6 |
| 2. 大租户刷流量时，小租户的延迟会受影响吗？ | **会，除非给它一个并发预算。** 同一场景下受害租户单条事件的 p99：无预算 4 278ms → 预算 4 时 **639ms（−6.7×）**；集成测试里（1 500 条预置洪水）190ms vs 4 584ms（−24×） | §7 |
| 3. 过载 3 倍时是降级还是雪崩？ | **取决于水位线。** 水位线 10 000 时：p50 905ms、p99 2.7s、积压 10 258 行；水位线 200 时：p99 **84ms**、92% 请求 2.3ms 内被 429 拒绝、积压 15 秒内归零 | §8 |
| 4. 一条投递慢，慢在哪一段？ | `X-HookFlow-Trace-Id` + W3C `traceparent` 一路传到接收方；`TracingIT` 断言接收方看到的 trace id 与 API 返回的一致（5 跳一条 trace） | §9 |

## 3. 方法：为什么不用 ab / k6

`ab`、`k6`、`JMeter` 默认都是**闭环**压测：一个虚拟用户发一条、等响应、再发下一条。系统变慢时压测器跟着变慢，于是**在慢的这段时间里本该堆积的请求根本没被发出去**。这叫 **coordinated omission**，它系统性地低估 p99。

本项目的做法：

1. `dev.hookflow.tools.LoadGen` **按固定速率**发压：第 `i` 条请求的应发时刻是 `start + i/rate`，与上一条何时返回无关。
2. 同一次运行里同时记录两个视角：
   - **开环**：`完成时刻 − 应发时刻`（含"因为系统慢而等待"的时间）——描述用户体验；
   - **闭环**：`完成时刻 − 实际发出时刻`——闭环工具会报的那个数。
3. 两者之差就是 coordinated omission 的量化值，直接印在结果里（`p99 inflation x…`）。

### 同一次运行，两个数字

600 req/s（应发）落在 64 个发送线程、水位线 10 000 的那次运行（[原始输出](perf/2026-10-22/600-default-watermark-64threads/loadgen.txt)）：

| 分位 | 开环（修正后） | 闭环（朴素工具会报的） | 低估倍数 |
|---|---|---|---|
| p50 | **905 ms** | 18.9 ms | 48× |
| p95 | 2 631 ms | 172 ms | 15× |
| p99 | **2 714 ms** | 229 ms | **11.9×** |

**这就是"不加修正的压测没有意义"的完整证明**：同一批请求，只因为客户端计时起点不同，p99 差了 11.9 倍。而且注意 p99 inflation 只在系统真的过载时才明显——100 req/s 的稳态下它是 1.3×，这恰好说明这个指标本身是可信的。

## 4. 稳态阶梯：容量在哪里拐弯

每组 30s（另有 5s 预热），2KB payload，开环，100% 成功除非另有说明。

| 应发速率 | 实际达成 | 成功率 | p50（开环） | p95 | p99 | 原始输出 |
|---|---|---|---|---|---|---|
| 100 req/s | 100.0 | 100% | 28.7 ms | 38.6 ms | 48.2 ms | [run1](perf/2026-10-22/100-baseline-run1/loadgen.txt) |
| 100 req/s | 100.0 | 100% | 29.3 ms | 39.4 ms | 48.2 ms | [run2](perf/2026-10-22/100-baseline-run2/loadgen.txt) |
| 100 req/s | 100.1 | 100% | 30.5 ms | 42.2 ms | 50.6 ms | [run3](perf/2026-10-22/100-baseline-run3/loadgen.txt) |
| **300 req/s** | **300.1** | **100%** | **32.7 ms** | 48.1 ms | **110.6 ms** | [32 线程](perf/2026-10-22/300-baseline-32threads/loadgen.txt) |
| 450 req/s | 461.4 | 65.7%（其余 429） | 35.8 ms | 636 ms | 750 ms | [48 线程](perf/2026-10-22/450-default-watermark-48threads/loadgen.txt) |
| 600 req/s | 629.1 | 47.9%（其余 429） | 905 ms | 2 631 ms | 2 714 ms | [64 线程](perf/2026-10-22/600-default-watermark-64threads/loadgen.txt) |

读法：

- **300 req/s 是干净的**：100% 接受，p99 110ms，远低于"p99 < 500ms"的目标。
- **450 req/s 开始出现 429**：不是服务器崩了，是 outbox 积压在这 30 秒里越过了默认的 10 000 行租户水位线（见 §8）。也就是说，**投递侧能持续消化的速率低于 ingest 侧**，差额堆在 outbox 里。
- 因此本文给"容量"的定义是：**在积压不增长、p99 < 500ms 的前提下能持续接受的速率**，本机约 **300–350 events/s**。

### 测量本身犯过一次错（值得记下来）

第一轮只有 **4 个发送线程**，我得到的结论是"容量 ≈ 175 req/s"。那是错的：

```
4 线程 × (1 / 23ms 服务时间) ≈ 175 req/s   ← 压测器的上限
```

把线程数提到 32 之后，同样的 300 req/s 达成率 100%、p99 110ms。**压测器成了瓶颈，而报告差点把它写成服务器容量。** 保留这个错误的原因写在 §11。

## 5. 瓶颈判定：证据而不是猜测

### 5.1 GC 不是（每个场景都一样）

`-Xlog:gc*` 统计（每次运行结束自动汇总成 `gc-summary.txt`）：

| 场景 | Young GC 次数 | 总停顿 | 最大单次停顿 |
|---|---|---|---|
| 100 req/s ×3 | 21 / 23 / 22 | 85–93 ms | 8.7–9.5 ms |
| 300 req/s | 28 | 104.8 ms | 10.4 ms |
| 600 req/s（水位 200） | 26 | 100.0 ms | 11.9 ms |
| 600 req/s（默认水位） | 33 | 127.1 ms | 10.1 ms |

35 秒里的总停顿是 85–127 ms，**占 wall time 的 0.24%–0.40%**；最大单次停顿 12ms，而 p50 是 29ms。GC 无论如何解释不了延迟，更解释不了吞吐。

### 5.2 G1 调参前后对比（结论：没用，但要知道为什么）

同一负载（100 req/s × 30s）、同一堆（512m），只改收集器参数：

| | p50（开环） | p95 | p99 | GC 次数 | GC 总停顿 | 最大停顿 |
|---|---|---|---|---|---|---|
| 默认（`MaxGCPauseMillis` 200） | 29.5 ms | 42.5 ms | 52.0 ms | 21 | 85.8 ms | 9.2 ms |
| `MaxGCPauseMillis=20` + `IHOP=25` | 29.6 ms | 43.0 ms | 50.4 ms | 32 | 82.0 ms | **5.7 ms** |

调参把**最大停顿减半（9.2 → 5.7ms）**，但 p50/p99 在噪声范围内不变。原因很简单：GC 只占 0.25% 的时间，把它优化到 0 也换不来 1% 的吞吐。**不测就调参，调的是心理安慰。**

### 5.3 JFR：进程基本在等 I/O

600 req/s（水位 200）那次运行的 JFR（`jfr.jfr`，约 78s 进程存活）：

| 事件 | 次数 | 累计时长 |
|---|---|---|
| `jdk.ThreadPark` | 35 745 | 1 270 158 ms |
| `jdk.SocketRead` | 7 470 | 312 592 ms |
| `jdk.ExecutionSample` | 285 | 3 170 ms |
| `jdk.GCPhasePause` | 26 | 587 ms |
| `jdk.JavaMonitorEnter` | 61 | 1 348 ms |

- 78 秒里**被采样到的 on-CPU 时间只有 3.2 秒**（≈0.04 个核），CPU 不是瓶颈；
- `SocketRead` 累计 313 秒 ≈ **平均 4 个线程同时阻塞在 socket 读**（MySQL 与出站 HTTP）；
- CPU 采样里最大的帧是线程池调度本身（`ThreadPoolExecutor.runWorker`，15/285），唯一像业务代码的是 Jackson 的 `UTF8StreamJsonParser._finishAndReturnString`（8/285 ≈ 2.8%）。

> 说明：`ExecutionSample` 只采样**正在跑**的线程，所以"样本很少"本身就是结论——线程几乎都在等。

### 5.4 连接池不是瓶颈

所有运行里 `hikaricp_connections_pending = 0`（没有线程在等连接），池上限 16，平均每次占用 2.2–4.7ms。**加大连接池不会有任何收益**，这一点用数据排除掉了猜测。

### 5.5 真正的成本中心：一个 ingest 一个事务 + 一次 fsync

服务端自身耗时（`http_server_requests_seconds_sum / count`，`POST /v1/events`，202）：

| 场景 | 平均服务端耗时 | 最大 |
|---|---|---|
| 300 req/s，默认 fsync | 见下 | 68 ms |
| 300 req/s，`innodb_flush_log_at_trx_commit=2` | 16.2 ms | 68 ms |

**改动前后对比（A/B，唯一变量 = 提交持久化策略，300 req/s × 32 线程，两次都 100% 成功）：**

| `innodb_flush_log_at_trx_commit` | p50（开环） | p95 | p99 | 原始输出 |
|---|---|---|---|---|
| 1（每次提交 fsync） | 32.7 ms | 48.1 ms | 110.6 ms | [输出](perf/2026-10-22/300-baseline-32threads/loadgen.txt) |
| 2（每秒刷一次盘） | **24.7 ms（−25%）** | **37.3 ms** | **67.7 ms（−39%）** | [输出](perf/2026-10-22/300-fsync2-32threads/loadgen.txt) |

**效果**：p99 −39%。
**代价**：崩溃（断电/内核 panic）可能丢掉最近 **1 秒**已提交的事务。本项目把 MySQL 当唯一真相源，所以这个改动**不作为默认值**——列在这里是为了说明"瓶颈确实在这一层"，而不是为了刷榜。

**没测到的部分，不猜**（v0.4 已部分补上）：一个 ingest 的服务端耗时 16–23ms，而单次连接占用只有 2–5ms，剩下的时间花在"语句之间的往返次数"还是"事务内的锁等待"上，v0.3 没有做到单语句粒度的测量，所以当时不写结论。[§15.4](#154-新瓶颈是-hookflow_outbox_published_total每行-24-ms-花在两处) 用 MySQL 的语句摘要把这件事拆开了：**批量入口下一次 ingest 批事务约 14.5ms，其中三条多行插入合计约 1.9ms，其余 12.6ms 是那次提交（fsync）**——也就是说"16–23ms"里语句本身只占 10%–15%，剩下的是提交。仍未单独计时的只有"语句之间的往返"，它现在被包含在"提交 − 语句"的差额里，量级上是毫秒级、不是数量级问题。

## 7. 公平性：一个预算把 4.2 秒变成 0.64 秒

场景：租户 A 以 60 req/s 灌入（接收方每次慢 200ms，制造队列），租户 B 在这期间提交 **10 条**事件（接收方快，200ms 延迟只加在 A 的端点上，这样 B 的延迟几乎全是"排队等待别人"）。唯一变量是 A 的 `max_in_flight`：

| A 的并发预算 | B 的 p50 | B 的 p95 | B 的 p99 | B 完成时 A 还积压 |
|---|---|---|---|---|
| 4（v0.3） | **414 ms** | 639 ms | **639 ms** | 1 054 |
| 0（不限 = v0.2 行为） | 4 196 ms | 4 278 ms | **4 278 ms** | 789 |

[原始输出](perf/2026-10-22/fairness-ab/fairness.txt)（`fairness.json` 同目录）

p99 **−6.7×**，而且注意"B 完成时 A 还积压"两行几乎一样（1 054 vs 789）——**积压没有变少，只是不再挡在 B 前面**。这正是 ADR-0009 声称的机制：预算限制的是"前面有多少条"，不是"总共有多少条"。

集成测试里用 1 500 条预置洪水、50ms 接收方，重复跑了三次（同一台机器、不同时刻）：

| 运行 | 有预算（`max_in_flight=4`） | 无预算 | 比值 |
|---|---|---|---|
| 1 | 146 ms | 4 172 ms | 28.6× |
| 2 | 190 ms | 4 584 ms | 24.1× |
| 3 | 316 ms | 3 794 ms | 12.0× |

`FairnessIT` 断言的是**方向**（有预算 < 2 000ms、无预算 > 2 000ms、比值 > 3），而不是某个具体毫秒数——**桌面上跑出来的绝对值不可复现，方向和量级可以。**

## 8. 过载 3 倍：降级还是雪崩

应发 600 req/s（约为容量 300–350 的 1.8–2 倍，也是本机可稳定生成的上限附近），64 发送线程，30 秒。唯一变量 = **租户积压水位线**：

| 指标 | 水位线 10 000（默认） | 水位线 200 |
|---|---|---|
| 实际达成 | 629 req/s | 600 req/s |
| 成功率 | 47.9% | 7.9% |
| 429 比例 | 52.1% | **92.1%** |
| p50（开环） | 905 ms | **10.9 ms** |
| p95 | 2 631 ms | 44.8 ms |
| p99（开环） | 2 714 ms | **84.1 ms** |
| p99（闭环） | 229 ms | 76.5 ms |
| 结束时 outbox 积压 | 10 258 行 | 302 行 |
| 15 秒后积压 | 未测（已超时） | **0** |
| 原始输出 | [输出](perf/2026-10-22/600-default-watermark-64threads/loadgen.txt) | [输出](perf/2026-10-22/600-watermark200-64threads/loadgen.txt) |

这张表就是计划里那句话的答案：

- **水位线定得太高 = 雪崩形态**：所有人一起等 0.9 秒，一半人最后还是被拒；
- **水位线定得合理 = 降级形态**：绝大多数请求在 **2.3ms** 内拿到 429 + `Retry-After`，被接受的那 7.9% 在 11ms 内完成，积压 15 秒内清零。

**这不是"调参让它变快"，而是"选择失败的方式"**：同样 600 req/s 的到达率，两种水位线都拒绝了一半以上的请求，但一种拒绝得干净、一种把所有人拖慢 100 倍。

> 注意：默认 10 000 的选择是**为了不丢数据、不把 MySQL 写爆**，不是为了保延迟。真正生产该按 `目标等待时间 × 排空速率` 来定（本机排空 ≈ 300/s × 5s ≈ 1 500），这条写进了 ADR-0010。

## 9. 一条 trace 串起 5 跳

`TracingIT`：真实 HTTP 请求 → API 响应头 `X-HookFlow-Trace-Id` → 接收方收到的 W3C `traceparent`，断言**同一个 trace id、不同 span id**。

```
api (HTTP span) -> relay (hookflow.publish, PRODUCER) -> worker (hookflow.delivery, CONSUMER)
                                                        -> hookflow.receiver (CLIENT) -> 客户接收方
```

链路证据不是"能导出 span"，而是**同一条投递在两端是同一个 trace**。本地看耗时的命令见 README 的「可观测」一节（Jaeger UI，4318 OTLP/HTTP）。

## 10. 从这台机器推到 4C8G

不做简单的线性外推，而是用测出来的**单位成本**推：

本机测得的稳态单位成本（2KB payload，100–300 req/s 区间）：

| 成本项 | 实测 | 说明 |
|---|---|---|
| 每事件服务端耗时 | 16–23 ms（视 fsync 策略） | §5.5 |
| 其中 DB 连接占用 | 2–5 ms | `hikaricp_connections_usage_seconds_*` |
| 每事件提交次数 | 1 次事务提交（≈7 条语句） | 代码路径固定 |
| GC 开销 | 0.25–0.40% wall time | §5.1 |
| CPU 占用 | ~0.04 核（等待为主） | §5.3 |

既然瓶颈是**串行化的 I/O 往返**而不是 CPU，那么 4C8G 与 14C/20T 的差别主要在：

1. **可以并发的连接数**：如果把 `DB_POOL_SIZE` 从 16 提到 32，本机不会更快（`pending=0` 已证明），但 4C 机器上 16 连接可能先撞上限；
2. **MySQL 与应用的 I/O 竞争**：同机部署时 4C8G 更容易互相拖慢，比 CPU 核数的影响大；
3. **GC 的堆余量**：512m 堆在 0.04 核的分配速率下绰绰有余，4C 机器上同样够。

因此 `docs/capacity.md` 给出的 4C8G 结论是**区间 + 判据**（例如"若 p99 目标 500ms 且单事件服务端成本 20ms，单实例 ≈ 16 连接 × (1000/20) ≈ 800 events/s 的理论上限，但实测只能到 300–350，缺口在事务内的串行等待"），并且明确写了**没有 4C8G 机器可以实测**这件事。

## 11. 测量本身的三个错误（留档，不隐藏）

1. **4 线程压测器被当成了服务器容量。** 见 §4 末尾。教训：先证明压测器不是瓶颈（发送线程数 × 1/服务时间 ≫ 目标速率），再谈容量。
2. **脏数据库。** 第一版没有清库，上一轮留下的 4 577 条 PENDING delivery 让"受害者"的 10 条事件排在它们后面，测出来全是 0ms。现在 `bench.ps1` 默认在启动前清库（`-KeepData` 可以保留）。
3. **JFR 是 0 字节。** 应用是被 `kill` 掉的，`dumponexit=true` 不会执行。现在脚本在杀进程前显式 `jcmd JFR.dump`。

这三个都是"测量方法"层面的错误，不是代码缺陷——但如果不修，§3–§8 的每一个数字都会是错的。**先修测量，再报数字。**

## 14. 附：v0.4 批量提交（同一到达率，事务数 1/20）

> 这一节是 v0.4 第 1 轮（A2）的补充测量，回答的问题与前 13 节不同：不是"这台机器最多能接多少事件"，而是"同样的到达率下，把 20 条事件塞进一个事务，延迟能换回多少"。**这里的成功率指 API 接受（202/200），不是投递成功**——下游排空速度没变，见 §14.5。

### 14.1 怎么测的

`scripts/bench.ps1 -Scenario api`，与 §2 同一台机器、同一天、同一套依赖容器；唯一变化的变量是"一个 HTTP 请求带几条事件"：

| 项 | 值 |
|---|---|
| 生成器 | `tools/LoadGen`，开环固定速率；`--rate` 始终是 **events/s**，批量模式把请求频率自动降到 `rate / batchSize` |
| 请求形态 | 单条 `POST /v1/events`（1 条/请求）；批量 `POST /v1/events/batch`（20 条/请求） |
| payload | 2 KB / 事件 |
| 应用 | `all` 单进程，`-Xms512m -Xmx512m`，`--hookflow.relay.interval-ms=200`、`--hookflow.fairness.refresh-interval-ms=500` |
| 水位线 | **显式关掉租户级降载**（`--hookflow.backpressure.tenant-high-watermark=1000000`）。`all` profile 为演示把它设成 200，不覆盖的话测到的是降载延迟（§14.4 记了这个坑） |
| 原始输出 | [`docs/perf/2026-10-23-batch/`](perf/2026-10-23-batch/)（含改造前 baseline 的两次对照） |

### 14.2 结果

单条路径：300 events/s，改造前后各两次（为什么各跑两次见 §14.3）：

| 运行 | 成功 | 开环 p50 | p95 | p99 | 闭环保 p99 |
|---|---:|---:|---:|---:|---:|
| baseline run1（`37ad12b`） | 100% | 40.4 ms | 81.6 ms | 162.6 ms | 107.5 ms |
| baseline run2 | 100% | 37.0 ms | 52.3 ms | 64.0 ms | 51.4 ms |
| 改造后 run1 | 100% | 43.7 ms | 120.5 ms | 174.8 ms | 145.9 ms |
| 改造后 run2 | 100% | 38.5 ms | 221.8 ms | 289.0 ms | 185.9 ms |

批量对照（改造后，各一次）：

| 场景 | 标称到达率 | 成功 | 开环 p50 | p95 | p99 |
|---|---:|---:|---:|---:|---:|
| 单条 | 300 events/s | 100% | 37.0–43.7 ms | 52.3–221.8 ms | 64.0–289.0 ms |
| 单条 | 450 events/s | 100% | **1 104.7 ms** | 2 200.5 ms | **2 314.2 ms** |
| 批量 20 | 450 events/s | 100% | **42.7 ms** | 62.9 ms | **69.5 ms** |
| 批量 20 | 900 events/s | 100% | 42.7 ms | 730.2 ms | 1 391.4 ms |

**读法（只说测到的）**：

- 到达率 450 events/s 时，单条路径的**中位**排队延迟是 1.10 s、p99 2.31 s；同样到达率下批量是 42.7 ms / 69.5 ms。中位数差 26 倍、p99 差 33 倍，方向与幅度都远超本节的 run-to-run 噪声。
- 批量在 900 events/s（单条路径稳态的 3 倍）仍然 100% 接受，p50 仍是 42.7 ms；p95/p99 涨到 730 ms / 1.39 s，说明 900 已经接近新的拐点。
- 单条路径在 300 events/s 下四次运行全部 100% 接受、p50 在 37–44 ms；p99 的散布是 64–289 ms。**没有证据说单条路径被拖慢了，但这次实验也不足以证明 p99 没有 10–20% 的退化**——按本项目的规矩，这一条只能写"未测出差异"。

### 14.3 为什么单条路径的 p99 不能用来做结论

同一份代码、同一台机器、同一组参数，两次 300 events/s 运行的 p99 分别是 64.0 ms 和 289.0 ms（4.5 倍）。原因没有归因到底，但足以说明：**这个量级的 p99 差值不能当作改动效应**。四次运行的 `metrics.txt`/`db.txt` 显示它们处理的事件量与 outbox 积压（6 867–6 946 行）几乎一致，所以不是"某次跑得更久"。

GC 也不是解释：七次运行的 GC 暂停总计 108–172 ms（26–29 次，单次最大 27 ms，见各目录的 `gc-summary.txt`），约占墙钟的 0.5%——它解释不了 4.5 倍的 p99 差异，更解释不了 450 events/s 下 1.1 s 的中位排队。

v0.3 的 §11 记过三个测量错误；这一节是第四个教训：**在同一台桌面机上，p99 的 run-to-run 散布可以大于任何合理的代码改动效应**。要回答"有没有 10% 的退化"，需要更多重复或一台安静的机器，这里没有做，也不声称做了。

### 14.4 两个踩过的坑（复现时会遇到）

1. **`all` profile 的演示水位线会污染容量测量**。第一版直接跑 `-Scenario api -Rate 300`：`application-all.yml` 把租户水位线设成 200，结果 87.8% 的请求是 429，延迟看着很漂亮——那是拒绝的延迟。`scripts/bench.ps1` 现在在 `api` 场景默认覆盖这个值（`overload` 场景仍按传入值，因为水位线本身是那个场景的变量）。
2. **线程数必须与到达率匹配**。生成器是开环的，但每个线程仍是"发一个、等一个"：4 个线程在 300 events/s、单请求约 30 ms 时只能发出约 130 req/s，剩下的一直在追到期时间，开环 p50 会涨到 18 秒——看起来像平台崩了，其实是生成器自己的瓶颈。v0.3 的 300/450/600 分别用 32/48/64 线程就是这个原因。

### 14.5 这批数字**没有**证明什么

- **不是投递容量**。成功率是 API 接受（202/200）。这些运行里 outbox 在 25 s 内只发布了 681–777 行、积压约 6 900 行——下游 relay 的逐条同步 confirm 才是现在的限速点（v0.4 计划的 G-4/B2，本次未做）。所以"900 events/s"说的是**入口**，不是"平台每秒送到客户 900 条"。
- **不是多进程拓扑**。全部是 `all` 单 JVM。
- **没有测批量大小的影响**（5 / 50 / 100 条），也没有测"批量 + 多客户端"——本节只比较 1 条/请求与 20 条/请求。
- **没有压到批量路径的失败边界**：900 events/s 仍然 100% 成功，没有出现 503/429，所以"批量接口在过载时的行为"本节没有数据（`BatchIngestIT` 只覆盖语义，不覆盖过载）。

## 15. A2 之后的下游：瓶颈从入口搬到了 relay（v0.4 B0）

> 这一节和 §14 问的不是同一个问题。§14 量的是**入口**（同一到达率下，20 条塞进一个事务能换回多少延迟）；
> 这一节量的是**出口**：把入口成本压平之后，平台**每秒真正能送到客户**多少，以及它卡在哪。
>
> 结论先写在这里：**新瓶颈是 `hookflow_outbox_published_total` 的速率——约 41 events/s，与入口是 450 还是 900 无关。**
> 卡住它的不是 worker、不是 DB 提交、不是连接池、不是锁，而是 relay **逐条**做「发布 + 等 publisher confirm + 单独 UPDATE 一行」
> （[§16](#16-b4relay-批量发布之后) 是把它批量化之后的数字）。

### 15.1 怎么测的

三次运行，同一台机器（§2）、同一天、同一套容器；唯一变量是**入口形态与到达率**：

| 运行 | 入口 | 标称到达率 | 线程 | 原始输出 |
|---|---|---|---:|---|
| 单条 | `POST /v1/events`，1 条/请求 | 450 events/s | 48 | [`single-450/`](perf/2026-10-23-downstream/single-450/) |
| 批量 20 | `POST /v1/events/batch`，20 条/请求 | 450 events/s | 16 | [`batch20-450/`](perf/2026-10-23-downstream/batch20-450/) |
| 批量 20 | 同上 | 900 events/s | 24 | [`batch20-900/`](perf/2026-10-23-downstream/batch20-900/) |

每次是**10 s 预热 + 60 s 负载 + 20 s 观察期**。观察期是这一节的关键：没有它只能看到"积压涨了多少"，
看不到"负载停下之后它会不会落"，而这两件事对判断瓶颈的作用完全不同。

`scripts/bench.ps1` 为这一节加了三个参数（都被 `meta.txt` 记录下来，可以复现）：

- `-SampleSeconds 5`：每 5 秒同时读三个地方——`/actuator/prometheus`（服务自己报的计数）、
  MySQL 的行数（积压**真的**在哪里）、broker 的队列深度与消费者利用率（worker 忙还是闲）；
  逐行写进 `series.csv`，再折算成每秒速率写进 `downstream.txt`。
  **一个跑完才取一次的快照回答不了这个问题**：快照只说"攒了多少"，不说"还在不在攒"。
- `-TailSeconds 20`：负载停止后继续采样，得到曲线的第三段（涨 / 平 / **落**）。
- `-StatementDigest`：跑之前清空 MySQL 的 `events_statements_summary_by_digest`，跑完把按摘要聚合的
  耗时导出成 `statements.txt`。这就是 v0.4 计划里 B3 要的那张分解表，本来要单独跑一次，这里顺手拿到了。

broker 一侧走 `rabbitmqctl`（`docker exec`）而不是 management HTTP API：这台机器上 15672 的每个
`/api/queues` 请求都会超时（本机代理），冷启动也不例外——记在 [§17](#17-这一节踩到的三个坑) 里，免得下一个人再试。

### 15.2 「批量前后 × 下游速率」

**出口速率（`hookflow_outbox_published_total` 的每秒增量）**，同一列对比三种入口：

| 入口 | 到达率 | **出口 publish/s（负载段）** | min–max | 负载停止后（观察段） | 积压增长/s | worker 队列 depth | broker unacked |
|---|---:|---:|---:|---:|---:|---:|---:|
| 单条 | 450 events/s | **30.2** | 24.4–33.8 | **43.2–46.7** | 421 | 0 | 1–3 |
| 批量 20 | 450 events/s | **41.5** | 38.7–44.3 | **45.3–46.4** | 398 | 0 | 1–3 |
| 批量 20 | 900 events/s | **39.3** | 35.4–41.6 | **42.3–45.6** | 820 | 0 | 1–3 |

同一批运行里，被超过的那几项（全是"没有咬合"的证据）：

| 指标 | 单条 450 | 批量 450 | 批量 900 |
|---|---:|---:|---:|
| `hikaricp_connections_pending` | **36 → 15 → 0** | 0 | 0 |
| `hookflow.db.lock_conflict_total` | 0 | 0 | 0 |
| `hookflow.outbox.publish_rejected_total` | 0 | 0 | 0 |
| broker `messages_ready` | 0 | 0 | 0 |
| 结束时 outbox 未发布行 | 29,554 | 28,928 | 59,771 |
| 结束时 delivery PENDING | 28,971 | 27,942 | 59,786 |

读法（只说测到的）：

1. **出口速率对入口不敏感**。入口从 450 提到 900（两倍），出口从 41.5 掉到 39.3——在噪声内。如果瓶颈在入口，
   这里应该翻倍。
2. **积压增长速率严格等于「入口 − 出口」**：450 − 41.5 ≈ 398（实测 398/s），900 − 39.3 ≈ 820（实测 820/s）。
   这是质量守恒：没有别的路径在丢事件，也没有别的路径在排空。
3. **单条路径在负载期间比批量低 27%（30.2 vs 41.5）**，但这不是"批量让 relay 变快了"：
   负载一停，两条曲线都回到 **43–47/s**。差别在负载期间——单条路径的 ingest 和 relay 抢同一批数据库连接
   （`hikaricp_connections_pending` 开局 36，批量那次全程 0），relay 的每一次 confirm 后面都排着别的提交。
   所以批量在这里的作用是**把入口从同一条队列里挪走**，而不是提高出口上限。
4. **出口上限（43–47/s）与入口形态无关**，这是 relay 自身的节拍。下一节解释它由什么构成。

### 15.3 积压堆在哪里：MySQL，不是 broker

900 events/s 那次跑完：outbox 未发布 **59,771** 行、delivery PENDING **59,786** 行，而 broker 队列里
`messages_ready` 全程 **0**、`messages_unacknowledged` 最多 **3**、消费者 **8** 个。

这就是 B0 分叉表第一行要求的三件事同时成立：

- 出口速率封顶，不随入口涨；
- **worker 是闲的**（队列空、每个消费者手里最多 1 条、8 个消费者加起来在途 ≤ 3）；
- 积压全部堆在 MySQL（这是 ADR-0010 的设计：broker 只是管道，积压属于 MySQL）。

如果反过来是 worker 卡住，看到的样子是 `messages_ready` 持续上涨、`unacked` 顶到 `concurrency × prefetch`。

### 15.4 新瓶颈是 `hookflow_outbox_published_total`，每行 24 ms 花在两处

出口 41.5/s → 每行 **24.1 ms**。`statements.txt`（同一窗口）把它拆开：

| 语句（digest） | 调用次数 | 平均 | 合计 | 属于谁 |
|---|---:|---:|---:|---|
| `UPDATE outbox SET status=?, published_at=NOW(?) WHERE id=?` | 4,070 | **12.4 ms** | 50.4 s | relay：**每发布一行一次单独提交** |
| `COMMIT`（所有事务） | 10,374 | 12.6 ms | 131.1 s | ingest / claim / settle / relay claim |
| `INSERT INTO event ... VALUES (...),(...)` ×20 | 1,575 | 0.94 ms | 1.5 s | ingest（批量，与 N 无关的固定几条） |
| `INSERT INTO outbox ...` ×20 | 1,575 | 0.52 ms | 0.8 s | ingest |
| `INSERT INTO delivery ...` ×20 | 1,575 | 0.48 ms | 0.8 s | ingest |

（批量 450 那次；900 与单条那两次的 top-3 与上表同序，数字见各自的 `statements.txt`。）

于是 24 ms 的构成是：

- **约 12.4 ms**：`markPublished` 是一条单行 UPDATE，自动提交 → 一次 fsync（`innodb_flush_log_at_trx_commit=1`）。
- **约 11 ms**：一次 `convertAndSend` + 一次 publisher confirm 往返（RabbitMQ quorum queue，确认前要落盘）。

两者都在 relay 的**同一个线程**里串行发生，所以 1 ÷ (12.4 + 11) ms ≈ 42/s，与实测 41.5/s 吻合。

**这也是 B3 的答案**（v0.4 计划里 B3 的问题是"耗时在调用往返还是语句"）：**一半一半**。
所以 B4 如果只批一半，天花板只有另一个一半：

| 只做哪一半 | 单行剩余成本 | 理论出口上限 |
|---|---:|---:|
| 只批量 confirm | 12.4 ms | ≈ 80/s |
| 只批量 `UPDATE outbox` | 11 ms | ≈ 90/s |
| **两个都批量**（B4 采用） | 每批一次 confirm 窗口 + 一次提交 | 见 §16 |

### 15.5 这一节修正了 §1 的一个说法

§1 写的是"约 300–350 events/s"。按本节的数据，那个数字是**入口接受**的上限，不是平台吞吐：
在 300 events/s 的 30 秒窗口里，429 之所以没有出现，是因为积压还没有越过 10 000 行的租户水位线
（450 events/s 的窗口里它就越过了，见 §4）。**积压一直在涨，只是 30 秒还不够长。**

在这台机器上，**持续吞吐 = 出口速率 ≈ 41 events/s**（B4 之前）。§14.5 已经写过一句
"不是投递容量，下游 relay 才是限速点"；本节把它量化了，并且给出了它卡在哪个指标上。
[capacity.md](capacity.md) §2/§3/§4 已按本节与 §16 重算。

### 15.6 这一节**没有**证明什么

- **不是多进程拓扑**。全部是 `all` 单 JVM，relay 单实例。B2 的多 relay 数据仍然没有。
- **接收方是本机 MockReceiver**（≈2 ms）。真实接收方 200 ms 时，worker 会先成为约束（capacity.md §4），
  那时出口速率不是 41/s，而是 `8 / 0.2 = 40/s` —— 恰好同一个量级，别把两件事混为一谈。
- **只有三次运行**，没做到能谈方差的次数（§14.3 的教训仍然有效）。出口速率这三次的散布是 35–47/s，
  所以"41/s"应该读成"40 上下"，不要读成小数点后一位。
- **没有压到平台水位线**。900 events/s 跑 60 s 只堆到 6 万行，离 100 000 行的 `outbox-high-watermark` 还很远，
  所以"过载到 503 之后出口怎么样"本节没有数据。
- **`statements.txt` 的窗口包含 app 启动和采样器自己的查询**（每 5 s 三条，占窗口内总耗时 < 0.1%）；
  `SELECT @@SESSION.transaction_read_only` 这类是连接池的固定开销，不是业务语句。

### 15.7 B0 的分叉：按观察选下一步

B0 的分叉表有四种观察，这次落在第一种：

| 分叉表的判据 | 本次观察 | 命中 |
|---|---|---|
| `outbox.published` 速率封顶、不再随入口涨 | 41.5/s（450 入口）→ 39.3/s（900 入口） | ✅ |
| worker 闲置 | `messages_ready=0`、`unacked≤3`、8 消费者；claim+settle 合计只占 8 个线程的 ~15% | ✅ |
| 积压堆在 MySQL | outbox 未发布 59,771 行 vs broker 0 条 | ✅ |
| `hikaricp_connections_pending > 0` 或某条语句占大头（DB 分叉） | 批量下 pending 恒 0 | ❌ |
| worker 忙 / 接收方延迟主导（worker 分叉） | 队列空、接收方 2 ms | ❌ |

→ **relay 是瓶颈 → 做 B4（relay 批量发布）**；B3 的语句拆解已经包含在上面（§15.4），
结论是"confirm 与 UPDATE 各占一半，两个都要批"。[§16](#16-b4relay-批量发布之后) 是 B4 之后的同一张表。

## 16. B4：relay 批量发布之后

> 做法与取舍见 [ADR-0014](adr/0014-batched-relay-publish.md)：一批消息**先全部发出、再一起等确认**，
> 确认过的 id **一条 UPDATE** 标记 PUBLISHED；未确认的一律放回 NEW。
> 采集命令与 §15 **完全相同**（同机、同到达率、同线程数），唯一变量是代码。
> 原始输出：[`docs/perf/2026-10-23-relay-batch/`](perf/2026-10-23-relay-batch/)。

### 16.1 同一张表，加了 B4 这一行

**出口速率（`hookflow_outbox_published_total` 的每秒增量）**：

| 入口 | 到达率 | 出口 publish/s（负载前 60 s，队列未到上限） | 观察期（负载停止后） | 积压增长/s | outbox 未发布（结束时） |
|---|---:|---:|---:|---:|---:|
| **B0 单条** | 450 | 30.2 | 43–47 | 421 | 29,554 |
| **B0 批量 20** | 450 | **41.5** | 45–46 | 398 | 28,928 |
| **B0 批量 20** | 900 | **39.3** | 42–46 | 820 | 59,771 |
| **B4 批量 20** | 450 | **400–466** | 1.4–1.9（队列到上限；排空后回升到 248） | **≈0（60 s 里 61 → 829 行）** | **731** |
| **B4 批量 20** | 900 | **390–460** | 1.7–2.5（同上） | **≈450（worker 追不上）** | 34,303 |
| **B4 单条** | 450 | 195–276 | 226–407 | ≈125（连接池被 ingest 占满，见 16.4） | 6,123 |

同一批运行里，**换谁在咬合**（这才是这一节的结论）：

| 指标 | B0 批量 450 | B4 批量 450 | B0 批量 900 | B4 批量 900 |
|---|---:|---:|---:|---:|
| relay 发布/s | 41.5 | **400–466** | 39.3 | **390–460** |
| worker 投递成功/s（整次运行均值） | 41.5 | **144**（末段 190） | 39.3 | **135**（末段 183） |
| broker `messages_ready` | 0 | **19 454（到 20 000 上限）** | 0 | **19 118（到上限）** |
| broker `unacked` | 1–3 | **64（= 8 消费者 × prefetch 8）** | 1–3 | **64** |
| `hikaricp_connections_pending` | 0 | 0 | 0 | 0 |
| 入口开环 p50 / p99 | 34.9 / 60.9 ms | 40.3 / **75.2 ms** | 34.9 / 82.7 ms | 41.0 / **103.5 ms** |

读法：

1. **relay 从 41 events/s 到 400–466 events/s（≈10.7×）**。450 入口那次的 outbox 积压在 60 秒里从 61 行到 829 行
   （B0 是每秒涨 ~400 行）——relay 不但追上了 450/s，还几乎不留存量。900 入口那次积压仍在涨，但涨幅从
   820/s 降到 ~450/s。
2. **900 入口那次测到的才是新上限**：入口 900/s，发布仍是 390–460/s，所以 **relay 的上限 ≈ 440/s**，
   不是"被入口抬上去的"。
3. **瓶颈换成了 worker**：两次批量运行的 `messages_ready` 都一路涨到 20 000 上限，`unacked` 钉在
   **64 = 8 消费者 × prefetch 8**（前端再也拿不到活），worker 整次运行只交付 135–144/s、末段 183–190/s。
   这就是 §15.7 分叉表的第三行：**下一个是 worker**，不是 relay、不是连接池、不是锁。
4. **入口延迟没有变快，也没有变慢**：450 那次 p99 60.9 → 75.2 ms，900 那次 82.7 → 103.5 ms，
   仍在 §14.3 记的 run-to-run 散布之内。**B4 换的是吞吐，不是入口延迟**——这个区别必须说清楚，
   否则下一个读文档的人会以为批量发布也让 API 变快了。
5. **单条入口那一列是反例，不是进步**：B4 之后单条 450 events/s 的开环 p50 是 **7.7 s**、p99 10.4 s，
   而 relay 只有 195–276/s、worker 只有 13–55/s。原因见 §16.4——它拆穿的是"单条入口能跑 450/s"这层假象。

### 16.2 为什么 relay 卡在 ~440/s 而不是几千

同一窗口的语句摘要（`statements.txt`）：`UPDATE outbox ... WHERE id IN (...)` 变成 **680 次调用、平均 46 行、
平均 22.0 ms**——每行 0.48 ms，是 B0 那版单行 UPDATE（12.4 ms/行）的 **1/26**。

那剩下的时间在哪？两个不再是"每行一次"、但仍然是"每批一次"的固定成本：

| 每批的固定成本 | 量级 | 说明 |
|---|---:|---|
| claim 事务（`SELECT ... FOR UPDATE SKIP LOCKED` + `markPublishing`） | ~16 ms（一次提交） | 每 tick 每轮一次 |
| `markPublishedBatch`（46 行一条 UPDATE） | ~22 ms | 一次提交 |
| 一个 confirm 窗口（46 条） | ~10–20 ms | 一次往返 |
| 46 条 JSON 反序列化 + 46 次 `convertAndSend` | ~5 ms | CPU |

46 行 ≈ 90–110 ms/批 ≈ **430–500/s**，与实测吻合。**下一个 10× 要动的是"每批一次提交"这件事**
（把 claim 与标记合并，或把 batch 从 50 提到更大），而不是再批 confirm——这属于之后的工作，本节不做。

### 16.3 队列上限被撞到之后发生了什么（失败路径的真实证据）

两次批量运行都在第 ~65 秒把 `hookflow.delivery` 顶到 `x-max-length=20000`。之后：

- publisher confirm 变成 **nack** → 计 `hookflow.outbox.publish_rejected` ≈ **175/s**；
- `releaseBackBatch` 把这些行**放回 NEW**（结束时 `NEW` = 731、`PUBLISHING` = 50）；
- relay 每 tick 提前返回（`publishBatch` 返回 false），发布速率掉到 ~2/s；
- 负载停止、队列被 worker 排空之后，发布自动恢复（末尾一段 225–407/s）。

这正是 [ADR-0010](adr/0010-backpressure-and-shedding.md) 写的形态：**broker 队列是一根小管子，满了就把行留在 MySQL**，
而不是让 broker 或 JVM 吃掉整个积压。区别在于 B0 之前从来没有真的撞到过它（41/s 永远填不满 20 000 行），
**B4 之后它是第一个会咬合的护栏**。

### 16.4 单条入口那次：池被 ingest 占满，不是 B4 的锅

B4 之后的 `single-450`（1 条/请求、450 events/s）看起来很差：开环 p50 **7.7 s**、p99 10.4 s、达成 403/s。
原因不是 relay 变慢，而是**批量发布把 worker 从"几乎不干活"变成"每秒上百次投递"之后**，单条入口的
450 次提交/s 与 worker 的提交叠加，把 16 个连接的池挤爆了：`hikaricp_connections_pending` 全程 **36–42**
（B0 那次只有开局 36，随后一直是 0）。

机制是一个正反馈：单条入口在 450 events/s 下，在途请求数 ≈ 到达率 × 服务时间。服务时间 20 ms 时是 9 个连接，
16 个的池还够；服务时间一旦被挤到 ~90 ms，在途就变成 ~40 个——池只有 16 个，于是 36–42 个线程在等连接，
服务时间继续涨，吞吐塌到 403/s、开环 p50 变成 7.7 s。B0 之前看不到这一幕，是因为下游几乎不消耗 DB。

换一句话说：**B0 之前，单条入口看起来"能跑 450/s"，是因为下游几乎不消耗 DB**；B4 拆掉了那层假象。
这也解释了为什么 A2（批量入口）不是可选项——批量入口把入口的提交次数从 450/s 降到 ~45/s，池才有余额给下游。

### 16.5 这一节**没有**证明什么

- **没有证明新的上限是 relay 的极限**：440/s 是"每批一次提交 + 一个 confirm 窗口"的结果，不是硬件极限。
  §16.2 已经写明下一刀该切哪里。
- **worker 的 135–190/s 混着两件事**：并发从 2 爬到 8 的过程（`MQ_CONCURRENCY` 2 → `max-concurrency` 8），
  以及每次投递两次提交（claim + settle，各 ~16.4 ms）。本节没有把这两者分开测。下一步若要拆，
  应该用 B2 的形态（多 worker 进程）或把 `concurrency` 钉死再看。
- **队列上限 20 000 截断了观察**。900 入口那次在第 65 秒之后进入 nack 区，"worker 能不能追上 900/s"
  这个问题本节没有答案——它需要先把 worker 的并发/提交次数解决掉再测一次。
- **仍然只有三次运行、一台桌面机、单 JVM**。稳定性结论（例如"440/s 可以跑一小时"）没有。

## 17. 这一节踩到的三个坑（复现时会遇到）

1. **broker 的 management HTTP API 在这台机器上不可用**。每个 `/api/queues` 请求都超时（本机 7890 代理，
   而且 `bench.ps1` 为了启动子进程会把 `no_proxy` 从环境里删掉，于是连 `localhost` 也走代理）。
   现在采样器走 `docker exec ... rabbitmqctl -q list_queues --formatter json`，与读 MySQL 的方式一致。
2. **队列参数不同就不能重新声明**。`hookflow.delivery` 如果是由旧版本（没有 `x-max-length`）创建的，
   新版本启动时会每两秒报一次 `PRECONDITION_FAILED`，而旧队列继续服务——测到的是一套没有配置文件描述的拓扑。
   `bench.ps1` 现在在启动应用前先删掉两个队列，让它按 `application.yml` 重建。
3. **多构造器的 Bean 必须显式 `@Autowired`**（这条计划里已经有了，我还是踩了一次）。
   `DeliveryPublisher` 为了测试加了一个带 `Duration` 的构造器，结果应用启动直接
   `No default constructor found`；bench 只报"application never became healthy"，真正的原因在 `app.log` 里。

> 附注：bench 结束打印的目录清单里 `app.log` / `jfr.jfr` 可能是 `0`，那是 Windows 对**仍被打开的文件**返回的
> 目录项大小；进程被 `Stop-Process` 之后再看就有内容（这次 JFR 是 5.6 MB）。不要据此判断"JFR 又坏了"。
