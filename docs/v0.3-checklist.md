# v0.3 验收清单

主题：**用可复现的测量方法说清瓶颈在哪、扩容先加谁。** 计划里的红线是「测不出来就不写数字」，所以这张表的每一行都必须指向一份原始输出或一个可重放的测试。

## A. 多租户公平调度（计划 2.1）

| 项 | 状态 | 证明材料 |
|---|---|---|
| 大租户积压不再饿死小租户 | ✅ | `FairnessIT`：同一场景下受害租户 p99 **4 584ms → 190ms**（跑三次：28.6×/24.1×/12.0×，断言只看方向与量级） |
| 实测对照（不是只声称） | ✅ | [performance.md §7](performance.md)：无预算 p99 4 278ms → 预算 4 时 **639ms**；两行的"洪水仍积压"几乎相同（1 054 vs 789），证明积压没变少、只是不再挡在别人前面 |
| 按 `tenant_id` 分片队列 vs 单队列加权轮询的取舍 | ✅ | [ADR-0009](adr/0009-fair-scheduling.md)：分片只把队头阻塞缩小到 1/N 且引入跨分片无序；改为"在 outbox→broker 边界做准入"后无需分片即达标 |
| 加权轮询（`tenant.weight`） | ✅ | `WeightedRoundRobinTest`（8 例）：3:1 在 40 次内精确 30/10，最大间隔 ≤ 权重比，**不随队列长度增长** |
| 每 endpoint 并发上限（`endpoint.max_concurrency`，v0.2 未实现） | ✅ | `AdmissionControlTest.endpointCapBlocksOnlyThatEndpoint`：只挡该端点，同租户其他端点不受影响 |
| 运行时可调、不需要重启 | ✅ | 预算存在 `tenant` 表；生效延迟 ≤ `hookflow.fairness.refresh-interval-ms` |
| 记录"公平性测试顺带发现的缺陷" | ✅ | [failures/0007](failures/0007-cancel-vs-claim-deadlock.md)：批量取消 vs 逐行认领死锁；已加重试并有单测 |

## B. 背压与降载（计划 2.2）

| 项 | 状态 | 证明材料 |
|---|---|---|
| outbox 高水位 → 拒绝而不是无限写入 | ✅ | `BacklogGate`；`BacklogGateTest`（5 例）覆盖两级水位、状态码、`Retry-After` |
| 平台级 vs 租户级分开（否则一个租户的洪水变成全平台 503） | ✅ | `50301 OVER_CAPACITY` / `42902 TENANT_BACKLOG_EXCEEDED`；`BackpressureIT` 在真实 HTTP 上断言 429 + `Retry-After`，并验证恢复后重新放行 |
| broker 队列长度上限 + 明确拒绝语义 | ✅ | `x-max-length=20000` + `x-overflow=reject-publish`；relay 把行放回 `NEW`（`hookflow_outbox_publish_rejected_total`） |
| worker 有界线程池 | ⚠️ | listener 容器**固定**线程数（`concurrency == max-concurrency`）+ `prefetch` 有界。**诚实说明**：Spring AMQP 的 listener 容器没有"线程池满 → 拒绝策略"机制（ack 必须发生在消费线程），真正的决策点在入口；worker 侧只保留"消息到了但预算已满"的策略（`defer`/`requeue`，可配置、有指标） |
| 三种策略取舍写进文档 | ✅ | [ADR-0010](adr/0010-backpressure-and-shedding.md)：阻塞生产者 / 拒绝并 429 / 丢弃低优先级，以及为什么选第二种 |
| 压测：到达率 3 倍时是降级还是雪崩 | ✅ | [performance.md §8](performance.md)：水位 10 000 → p50 905ms、p99 2.7s、积压 10 258；水位 200 → p99 **84ms**、92% 请求 2.3ms 内拿到 429、积压 15 秒归零 |
| `max_in_flight` / `outbox_backlog` 能提前预警 | ✅ | 指标 `hookflow_outbox_backlog`（gauge）、`hookflow_ingest_shed_total{scope}`；告警阈值表见 [operations.md §3](operations.md) |

## C. 严格的延迟测量 + JVM 证据（计划 2.3）

| 项 | 状态 | 证明材料 |
|---|---|---|
| 不用闭环压测（coordinated omission） | ✅ | `dev.hookflow.tools.LoadGen` 按固定速率发压，**同一次运行同时输出开环与闭环两个视角** |
| 解释两个工具为什么给出不同数字 | ✅ | [performance.md §3](performance.md)：同一批请求 p99 905ms（开环）vs 229ms（闭环），相差 **11.9×**；稳态下这个比值只有 1.3×，说明指标本身可信 |
| wrk2 的 `--rate` | ⚠️ | 本机没有 wrk2 二进制、也拉不到镜像，所以**没有用 wrk2 跑过**。替代物是自研开环压测器（同一算法：按应发时刻计时）。`LoadGen` 与 wrk2 的差异（连接复用、统计方式）未做对拍——**这是一个真实缺口，不掩盖** |
| `-Xlog:gc*` + 停顿统计 | ✅ | 每次运行自动汇总 `gc-summary.txt`：35s 内 21–33 次 Young GC、总停顿 85–141ms、最大 8.7–11.9ms |
| JFR 抓分配热点 | ✅ | `jfr.jfr` 每次运行落盘（显式 `JFR.dump`，因为进程是被 kill 的）；`jdk.ObjectAllocationSample` 12–13k 样本，`ExecutionSample` 只有 285–442 个 → **基本没有 on-CPU 热点** |
| async-profiler 火焰图 | ⬜ | 本机未安装，镜像也拉不到。替代：JFR `ExecutionSample` 的 top-frame 统计（[performance.md §5.3](performance.md)）。**不声称做过火焰图** |
| G1 调参前后对比 | ✅ | [performance.md §5.2](performance.md)：`MaxGCPauseMillis=20`+`IHOP=25` 把最大停顿 9.2→5.7ms，**p50/p99 在噪声内不变**（因为 GC 只占 0.25% 时间） |
| 报告包含机器规格/配置/持久化/并发 | ✅ | [performance.md §2](performance.md)（含 CPU 型号、核数、内存、JVM 参数、Docker 参数、payload 大小） |
| 吞吐 + p50/p95/p99 + 错误率 + 队列积压 | ✅ | [performance.md §4/§8](performance.md) |
| 瓶颈判定（DB？网络？lease？火焰图指向哪） | ✅ | [performance.md §5](performance.md)：排除 GC / CPU / 连接池；`innodb_flush_log_at_trx_commit` A/B（p99 −39%）定位到 DB 提交 |
| 优化前后对比：改了什么、效果多少、代价是什么 | ✅ | fsync A/B：p99 110.6→67.7ms（−39%），代价 = 崩溃可能丢 1 秒已提交事务，因此**不作为默认值** |
| 原始命令与原始输出（可复现） | ✅ | 命令在 [performance.md §12](performance.md)；原始输出在 [docs/perf/2026-10-22/](perf/2026-10-22/)（每次运行的 loadgen/timeline/gc-summary/meta） |
| README 不出现未测的 QPS | ✅ | README 只引用 `performance.md` 的实测数字，并标明机器规格 |

## 一句话自评

**现在可以讲的**：单机 300 events/s（p99 110ms）的实测、瓶颈定位到 DB 提交并有 A/B 证据、公平性 4 584→190ms 的量化和机制、过载两种水位线下降级形态的对比、coordinated omission 的 11.9 倍实测差距、一条 trace 串起 5 跳的断言、以及**三个测量方法本身的错误**。

**还不可以讲的**：wrk2/async-profiler 的交叉验证、4C8G 的真实数字、多机拓扑下的容量、Jaeger UI 里的人工验证。

这些都在上面的表里标了 ⚠️/⬜，不是遗漏。
