# ADR-0008：故障注入用容器级操作，而不是网络代理

- 状态：已采纳（v0.2）
- 日期：2026-10-22

## 背景

v0.2 的目标是「可靠性主张必须由可重放的自动化测试证明」。为此需要能在 CI 里稳定制造三类故障：

| 编号 | 故障 | 要证明什么 |
|---|---|---|
| F1 | 接收方超时 / 连接被拒 | 错误被正确分类，且按语义决定是否重试 |
| F2 | broker 不可达 | 事件仍被接受、工作不丢、恢复后自动追平 |
| F3 | worker 崩溃 | lease 过期后由别人接手，陈旧写入被隔离 |

## 选项

| 方案 | 做法 | 优点 | 问题 |
|---|---|---|---|
| **A. Toxiproxy** | 在链路中插入 TCP 代理，注入延迟 / 重置 / 断流 | 是这类测试的「标准工具」，可精确控制 | 代理与应用/依赖必须在同一 Docker 网络里才能互达；在 Docker Desktop 上代理接受了 TCP 连接却到不了 upstream，客户端表现为 AMQP 握手超时——**看起来像应用 bug**。另外多一个镜像、多一层要调试的东西 |
| **B. 容器 stop/start** | 直接停掉依赖容器 | 真实（进程真的没了） | 重启后 Docker 可能重新分配宿主端口，而 Spring 的配置在启动时已固定 → 变成"连错误地址"的测试 |
| **C. 容器 pause/unpause** | 冻结依赖容器 | 端口映射不变；效果等价于 broker 僵死 / 网络分区 | 不能用来验证"进程重启后状态恢复" |
| **D. 进程内 TCP 代理（自研）** | 测试 JVM 内起一个转发 socket，按需延迟/重置 | 零基础设施、完全确定、不依赖 Docker | 只能覆盖接收方一侧；自己写的代理本身可能有 bug，且不模拟 broker |
| **E. 应用侧打桩** | 用 mock 的 publisher / 假错误 | 最快 | **测的是打桩，不是系统**。这正是要避免的 |

## 决定

按故障类型分别选最合适的工具，而不是强行统一：

| 故障 | 采用方案 | 理由 |
|---|---|---|
| F1 接收方超时 / 拒绝 | **在测试内起真实 HTTP 服务器，用"延迟"和"关闭端口"造故障**（方案 D 的简化版：不写代理，直接让服务器慢/不存在） | 最贴近真实客户行为，零基础设施，毫秒级确定 |
| F2 broker 不可达 | **容器 pause/unpause**（方案 C） | 保留端口映射；语义等价于 broker 僵死；unpause 后还能验证客户端重连，比 stop/start 更有价值 |
| F3 worker 崩溃 | **直接用 SQL 制造"崩溃后的状态"**（认领后租约过期、携带陈旧 token 写入） | 进程崩溃的**可观测后果**就是这些状态；直接构造状态比杀进程更精确、更快、更可重放 |

**明确放弃 Toxiproxy。** 不是因为不好，而是因为它在"代理与目标必须同网络 + 跨平台一致性"上的成本高于收益：本次尝试中，它的失败模式（握手超时）伪装成应用缺陷，浪费的调试时间本身就是论据。

## 代价

- 没有"带宽限制 / 半开连接 / 慢速滴流"这类精细的网络故障覆盖。若将来要做，Toxiproxy 仍是首选，前提是把它放在**同一个 compose 网络**里而不是 Testcontainers 临时网络
- F3 没有真的杀进程，因此**不能证明**「进程崩溃瞬间 OS 会关闭连接」这类运行时行为。这个靠一次性的手工演练（`docs/failures/` 里的 drill 记录）补，而不是靠 CI
- pause/unpause 依赖 Docker API，在某些受限的 CI（如远程 Docker 无 pause 权限）可能不可用；这类环境需要跳过 F2 测试而不是让它失败

## 什么是确定性的、什么只能靠演练

这个区分很重要，写下来避免以后自欺：

| 命题 | 能否自动化 | 由谁证明 |
|---|---|---|
| 超时被分类为 TIMEOUT 并重试 | ✅ 可以 | `ReceiverFaultIT` |
| 连接被拒被分类为 CONNECT_ERROR 并重试 | ✅ 可以 | `ReceiverFaultIT` |
| broker 不可达时事件仍被接受 | ✅ 可以 | `BrokerOutageIT` |
| broker 恢复后自动追平 | ✅ 可以 | `BrokerOutageIT` |
| 崩溃后租约过期被回收 | ✅ 可以（构造状态） | `EventIngestIT` |
| 陈旧 token 写入被隔离 | ✅ 可以（构造状态） | `EventIngestIT` |
| **确认后崩溃导致重复发布** | ✅ 可以（构造 PUBLISHING + 旧时间戳） | 目标：`OutboxCrashWindowIT` |
| kill -9 后进程真的立刻释放连接 | ❌ 只能演练 | 手工 drill 记录 |
| 真实 GC 停顿期间的租约续期 | ❌ 只能演练 | v0.3 压测时观察 |

## 如何验证这个决策是对的

- `ReceiverFaultIT` + `BrokerOutageIT` 在 CI 里稳定通过（连续两轮）
- 这套测试在 v0.2 期间真的抓到了一个 P1 缺陷（`docs/failures/0003`）：broker 停机时 outbox 行卡在 `PUBLISHING`，因为异常类型没被接住。这个缺陷在 v0.1 的全绿测试里完全不可见
