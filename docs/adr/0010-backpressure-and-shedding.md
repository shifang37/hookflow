# ADR-0010：过载时在入口淘汰，而不是在内部排队

- 状态：已采纳（v0.3）
- 日期：2026-10-22

## 背景

v0.2 的 outbox 没有长度上限、broker 队列没有上限、worker 线程池是弹性的，也没有任何拒绝策略。突发流量的结局不是降级，而是：

1. outbox 行数无上限增长 → MySQL 写入变慢 → 事件表也慢；
2. broker 队列无上限 → 内存与磁盘被单个队列吃掉；
3. worker 想跟上就无限加线程 → 上下文切换、GC 压力上升；
4. 最后所有请求一起超时，**已经接受的事件也投递不出去**。

这叫雪崩。降级的定义是：**拒绝一部分新工作，以保住已接受的工作。**

## 选项

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 继续无界接受** | v0.2 行为 | 雪崩；且"已接受"变成谎言 |
| **B. 阻塞生产者** | 不放行直到内部有空间 | HTTP 生产者无法被真正反压（TCP 窗口不是业务信号）。连接堆积的结果与 A 相同，只是更慢 |
| **C. 拒绝并给明确语义** | 超水位返回 `429`/`503` + `Retry-After` | 需要客户端配合退避；拒绝率上升会被监控看见（这是好事） |
| **D. 丢弃低优先级** | 队列满时丢低优先级工作 | 本项目**没有优先级概念**；引入优先级等于引入一个新的产品维度 |
| **E. broker `drop-head`** | 队列满时丢队头 | 丢弃的是**已经持久化**的工作。MySQL 里还有 delivery 行，但恢复要等一个 stuck-scan 周期，等于用正确性换空间 |

## 决定

三层各自承担一部分，**入口做淘汰，内部做上限**：

### 1. API 入口：两级高水位

| 水位 | 触发 | 响应 | 影响范围 |
|---|---|---|---|
| `outbox-high-watermark`（平台） | `COUNT(outbox WHERE status IN ('NEW','PUBLISHING'))` | `503` + `Retry-After` | 所有人——平台真的满了 |
| `tenant-high-watermark`（租户） | 同上，按 `tenant_id` 分组 | `429` + `Retry-After` | **只有该租户** |

两级分开是刻意的：只有一个租户在灌时，平台仍然健康，此时给所有人 503 就是把一个租户的问题变成全平台的问题——正是 ADR-0009 要消除的那种耦合。

计数是缓存快照（`check-interval-ms`，默认 500ms，单飞刷新）。在入口路径上对每个请求做一次 `COUNT(*)` 会让入口成本 O(积压)，这是最不该发生的事。

### 2. broker 队列：长度上限 + `reject-publish`

交付队列声明 `x-max-length` 与 `x-overflow=reject-publish`。队列满时 broker **拒绝**这条发布，publisher confirm 返回 nack，relay 把该 outbox 行放回 `NEW` 并停止本轮。

这是整个设计里最省事的一环：积压被推回 MySQL——它本来就在那儿。没有丢消息，没有额外组件，没有"重试队列"。

### 3. worker：有界并固定

listener 容器的线程数**固定**（`concurrency == max-concurrency`），`prefetch` 有界。饱和时的表现是 broker 不再投递，而不是 JVM 里堆任务。

顺带一个诚实的说明：**Spring AMQP 的 listener 容器没有"线程池满 → 拒绝策略"这个机制**，因为 ack 必须发生在消费线程上，容器不会把消息投递给一个不存在的线程。真正存在的"满了要不要继续等"的决策点在入口（第 1 层）。worker 侧唯一需要策略的是"消息到了，但这个租户/端点的预算已满"，见下。

### 4. worker 超预算时的策略（可配置）

`hookflow.worker.over-capacity-policy`：

| 值 | 行为 | 代价 |
|---|---|---|
| `defer`（默认） | 立即 ack，交给 `DeliveryRecovery` 重新入队 | 延迟 = `stale-publishing-seconds`（默认 60s）；饱和期间不耗 CPU |
| `requeue` | nack 并立即重投 | 延迟低；但预算一直满时会以 prefetch 的速率反复空转，烧一个线程的名额 |

## 为什么不在内部"缓冲一下再说"

因为**缓冲不是容量**。缓存把过载从"看得见的 429"变成"看不见的延迟"，而延迟最终会在某个点变成超时。入口拒绝的价值在于它诚实地告诉调用方"现在不行"，并给出 `Retry-After`——这个信息本身就是系统的一部分。

## 代价与已知问题

- 拒绝率上升意味着部分客户端必须能重试。不能重试的客户端（fire-and-forget）在过载时会丢事件——这是策略选择，需要写进 SLA。
- `Retry-After` 是约定而非协议强制；不听话的客户端会把 429 变成自我施加的重试风暴。
- 缓存窗口内可能多接受"一个窗口的量"，水位不是精确护栏。
- 队列长度上限**改不了**已存在的队列：RabbitMQ 拒绝对已声明队列改参数，本地开发需要删队列或 `docker compose down -v`。

## 什么情况下会改这个决定

1. 出现"不可丢"且"无法重试"的接入方式（例如同步 HTTP 回调给客户的客户）→ 需要引入优先级或持久化的拒收队列。
2. `reject-publish` 导致 relay 空转频次过高（可观测：`hookflow_outbox_publish_rejected_total` 与 relay CPU）→ 改为 relay 自己按队列深度提前减速，少一次网络往返。
3. 多租户额度真正商品化 → 水位从全局配置变成租户合约字段。

## 如何验证

- `BacklogGateTest`（5 个用例）：两级水位、状态码、`Retry-After`、计数只算一次。
- `BackpressureIT`：暂停 broker 造积压 → 真实 HTTP 观测到 `429` + `Retry-After`；恢复后**已接受的事件全部投递成功**，且租户被重新放行。
- 压测报告（`docs/performance.md` 过载一节）：3 倍到达率下 429 比例上升、p99 不爆炸、积压最终排空。
