# ADR-0013：批量摄入用「一个事务 + 每条自己的幂等键」，不做请求级事务

- 状态：已采纳（v0.4）
- 日期：2026-10-23

## 背景

ingest 的成本是「每事件一个事务 + 约 7 条语句 + 1 次 fsync」，容量测量（[performance.md §5.5](../performance.md)）显示瓶颈在 DB 提交。让容量上一个台阶，最直接的手段是让一个事务覆盖多条事件。

批量立刻引入一个新问题：**一个请求里有 N 个幂等键，其中一部分可能已经存在**。如果整批因为一条重复就失败，调用方就无法用批量做"重试那批没收到确认的"; 如果整批静默跳过重复，调用方不知道哪几条没写进去。

同时，"批量"会天然地绕开两个已有的保护机制：每租户限流（按请求计数）和入口水位线（按请求判断积压）。这个决定必须一起处理。

## 选项

| 方案 | 做法 | 代价 |
|---|---|---|
| A. 不做批量 | 现状 | 语义最简单；但容量停在单条事务的曲线 |
| B. 请求级幂等键 | 一个 `Idempotency-Key` 对应整批 | 一批里掺一条旧事件就必须整批重放或整批丢弃；调用方无法表达"这 20 条里 3 条我之前发过" |
| C. 逐条事务 + 部分成功 | 每条一个事务，逐条返回成功/失败 | 没有减少事务与 fsync，容量目标落空；部分成功还要求调用方自己记账"哪几条成功了" |
| **D. 一个事务 + 每条自己的幂等键 + 逐条 `replay` 标记（选中）** | 整批一个事务；已存在的键按条返回原 `eventId` + `replay:true`；新键写入 | 任一条触发非幂等类 DB 错误则**整批回滚**；单批必须有上限 |
| E. `INSERT IGNORE` + 读回 | 忽略一切重复键 | 会把数据截断、外键、类型等错误一起吞掉，错误语义不可控 |

## 决定

- `POST /v1/events/batch`，1–500 条，**每条自带 `idempotencyKey`**（没有请求级幂等头）。
- 一个事务，固定形状：多行 `INSERT event` → 按幂等键读回 id → 多行 `INSERT delivery` → 按 `event_id` 读回 id → 多行 `INSERT outbox`。
- 部分重复**不是错误**：按条返回 `{index, eventId, deliveryCount, replay}`；同批内重复的键解析到**第一次出现**创建的那个事件（`replay:true`）。
- 超过 500 条**整批 400，不截断执行**。
- 限流与降载按**事件数**计（一批 20 条要 20 个配额；按"当前积压 + 20"判断水位）。
- 并发撞上唯一键时：事务回滚 → 重读赢家 → 最多 3 次；仍读不到则 500（与单条路径的 pathological case 一致，见 [failures/0001](../failures/0001-idempotent-race-snapshot.md)）。
- 整批未提交（DB 不可用）→ `503 DEPENDENCY_UNAVAILABLE`，原样重试安全。

## 为什么

- **为什么不是 B**：幂等键的语义是"这一条事实的身份"，不是"这一批请求的身份"。请求级键会让"重发一批里 3 条旧事件"变成整批冲突，批量就失去了它最有用的场景（网络抖动后重试）。
- **为什么不是 C**：目标是减少事务与 fsync。逐条事务不减少提交次数，容量目标直接落空；部分成功还把一致性负担推给调用方。
- **为什么读回 id 而不是 `useGeneratedKeys`**：MyBatis 的多行 INSERT 拿不到可靠的自增 id 回填（本项目领域对象还是不可变 record，没有 setter）。在**同一个事务里**按自然键（幂等键、`event+endpoint`）读回，是一次索引查询换类型安全与可预测性。
- **为什么 500 条封顶且整批 400**：一个事务越大，锁持有时间、`max_allowed_packet` 风险、失败爆炸半径越大。500 条 × 2KB ≈ 1MB，即使按 64KB 的 payload 上限算也只有约 32MB，仍在 MySQL 默认 `max_allowed_packet`（64MB）之内。超过 500 的正确做法是拆成多个请求，而不是让一个请求变成不可预期的长事务。截断执行更糟：调用方会以为自己提交了 500 条。
- **为什么按事件数限流/降载**：否则批量就是绕过限流与水位线的最短路径（1 个请求 = 1 个配额 = 1 条积压）。

## 代价与已知问题

- **整批原子，不是部分提交**。一条坏数据会让整批失败，调用方要自己定位。因此校验全部前置在 controller（`eventType` / `payload` / `idempotencyKey`），只有 DB 级错误才可能触发整批失败。
- **500 × 每事件 endpoint 数**是一个事务的行数上限，没有对"单事件扇出到很多 endpoint"做额外限制。
- **批内同一个键、不同 payload** 时按第一次出现的 payload 写入（幂等键优先，不比较 payload）。这与单条路径一致——`40901 IDEMPOTENCY_KEY_REUSED` 在 `docs/api.md` 里列着，但从未真正实现 payload 比对。批量让这个语义更容易被注意到。
- 批量响应是**数组**，单条是对象；两种客户端要分别处理。
- "全部是重放"的批次有 3 条查询（按幂等键查、按 `event_id` 查计数、无插入），比逐条少，但不是零。
- **单条路径没有复用批量的执行路径**：两者共享 mapper 与 `OutboxWriter`，但单条事务形状不同（插入后立刻拿 id，再逐 endpoint 扇出）。合并会让单条路径多一次读回，因此保留了两份编排逻辑。

## 什么情况下会改这个决定

1. 单批 500 条不够（真实客户一次导入上万条）→ 做**异步接收 + 回执查询**，而不是把上限提大。
2. 出现"批内部分成功"的真实需求 → 提供 `partial=true` 的逐条事务模式，作为**独立端点**，不改变现有语义。
3. 幂等键 payload 冲突成为真实问题 → 实现 `40901`，单条与批量同时生效（那是一次 API 语义变更，需要单独 ADR）。
4. 多行 INSERT 的 id 回填在 MyBatis 里变得可靠 → 去掉两次读回。

## 如何验证

- `BatchIngestIT`（真实 HTTP + 真实 MySQL）：20 条夹 3 条已存在的键 → 20 个正确 `eventId`、事件与投递都不重复；整批重放 → `200` 且 id 不变；批内重复键 → 一个事件；501 条 → 整批 `400`。
- `TenantRateLimiterTest`：配额按事件数消耗；`BacklogGateTest`：批量按「积压 + N」判断。
- [performance.md §14](../performance.md)：同一到达率 450 events/s 下开环 p50 1.10 s → 42.7 ms；原始输出在 [docs/perf/2026-10-23-batch/](../perf/2026-10-23-batch/)。
