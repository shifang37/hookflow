# ADR-0004：模块化单体 + 按角色启动，而不是一开始就拆微服务

- 状态：已采纳（v0.1）
- 日期：2026-10-22

## 背景

这个系统的天然形态是三块：接收事件、把 outbox 变成消息、执行投递。看起来很像三个微服务。

## 决定

**同一份代码、同一个镜像，用 Spring profile 选择启动哪些 Bean：**

| profile | 启动的组件 | 扩容特性 |
|---|---|---|
| `api` | 控制器 + 鉴权过滤器 + 限流 | 无消费者，扩容不会放大投递 |
| `relay` | outbox relay + 卡死回收 | 靠 `SKIP LOCKED` 安全水平扩展 |
| `worker` | 消费者 + 投递执行 + 回收调度 | 靠 lease + attempt 护栏安全水平扩展 |
| `all` | 全部（仅本地演示） | — |

角色边界由 `@Profile` 和包结构共同表达，不是靠口头约定。

## 为什么

1. **扩容需求不同但代码相同**：真正需要独立扩容的是 worker（受外部接收方延迟影响），api 和 relay 可以同步扩。拆成微服务是为了独立部署，而"独立部署"用 profile 已经能拿到 90% 的收益。
2. **一个事务胜过三个服务**：事件摄入必须在**一个本地事务**里写 event + delivery + outbox（ADR-0001）。一旦拆服务，这个事务就没了，只能上 saga——为了架构美观而放弃最简单正确的方案，是本末倒置。
3. **调试成本**：单体里一次 `docker compose up` 就能复现问题；三个服务需要三个端口、三份配置、一套链路追踪才能看到同样的事。
4. **面试场景尤其重要**：面试官问"你为什么拆/不拆"，能回答"因为事务边界在这里，拆了就丢一致性，我选择先统一，等压测证明瓶颈再拆"远比"因为微服务流行"有价值。

## 什么情况下会改这个决定

明确的触发条件（不是"以后再说"）：

- worker 的扩容节奏与 api 出现**数量级差异**（比如 worker 需要 50 个实例、api 只要 3 个），且资源隔离成为瓶颈
- 投递逻辑需要独立发布节奏（比如支持插件化的传输协议）
- 团队规模超过 5 人，同一个仓库的合并冲突成为主要成本

在此之前，**跨模块调用一律走 Java 接口**，不引入 RPC。这样将来抽服务时，接口就是天然的切割线。

## 代价

- 单个镜像包含所有角色的依赖，镜像比纯 api 服务大
- 无法给不同角色配不同的资源限额（K8s 侧仍可用同一镜像 + 不同 profile 做到）
- 一个角色的 bug 可能导致整个进程 OOM（worker 的线程池被耗尽时）——靠有界线程池和超时缓解

## 如何验证

- `docker compose up -d` + `./mvnw spring-boot:run --spring.profiles.active=api` 应能独立启动且不消费消息（`application-api.yml` 里 `auto-startup: false`）
- 集成测试以 `all` profile 跑通，说明角色拆分没有破坏链路
