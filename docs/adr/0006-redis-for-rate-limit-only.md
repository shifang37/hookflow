# ADR-0006：Redis 只做限流，不存任何事件状态

- 状态：已采纳（v0.1）
- 日期：2026-10-22

## 背景

Redis 在这个项目里有一席之地（限流），但很容易被"顺手"用来做更多事：缓存 delivery 状态、做分布式锁、存队列、存幂等键。每一种用法都会引入新的失败模式。

## 决定

**Redis 只承担租户限流计数器。** 具体约束：

1. Redis 里存的只有 `hookflow:rl:tenant:{id}` 这样的计数键，TTL = 1 秒窗口
2. 事件、投递、attempt、outbox **一律不在 Redis**
3. 幂等性**只**依赖 MySQL 唯一键，不依赖 Redis 的 `SETNX`
4. 不用 Redis 做分布式锁（认领用 MySQL lease，见 ADR-0003）

## 为什么

| 如果 Redis 存了… | 会发生什么 |
|---|---|
| 幂等键 | Redis 重启/驱逐 → 同一事件被写入两次（唯一约束其实还在 DB，但"先在 Redis 挡一层"的说法就成了假的安全感） |
| delivery 状态 | 出现第二个权威源，缓存与 DB 不一致时需要处理脏读、双写、失效风暴——**而本业务不需要缓存**（查询量小，PK 查 MySQL 足够快） |
| 分布式锁 | 锁过期与 fencing 的问题跟 lease 一样，但没有数据库事务的原子性，等于用更弱的工具做同一件事 |

**判定标准很简单：这个数据丢了会不会导致客户数据丢失？** 限流计数丢了只会漏放一些请求，代价可控；事件状态丢了就是数据事故。所以只有前者可以放 Redis。

## Redis 挂了怎么办

这是一个**必须显式配置**的策略，不是意外行为：

```yaml
hookflow:
  rate-limit:
    fail-open: true
```

| 配置 | 行为 | 适用场景 |
|---|---|---|
| `fail-open: true` | Redis 不可用时限流放行，日志告警 | 默认。可用性优先：宁可让突发流量进来，也不要因为限流组件故障而拒绝全部业务 |
| `fail-open: false` | Redis 不可用时返回 `503 DEPENDENCY_UNAVAILABLE` | 保护优先：后端确实扛不住突发，宁可不收事件也不要被打垮 |

两种模式的代价都写进 README 和 `docs/operations.md`，运维必须知道自己在选什么。

## 限流实现细节

Lua 脚本一次往返完成计数与过期：

```lua
local current = redis.call('INCR', KEYS[1])
if current == 1 then
  redis.call('PEXPIRE', KEYS[1], ARGV[2])
end
return current
```

- 只在第一次自增时设置 TTL → 不会出现"调用越频繁窗口越往后延"的问题
- 单命令原子 → 不需要 WATCH / 事务
- 固定窗口而不是令牌桶 → 边界处可能放过 2 倍流量（窗口切换瞬间）。这是**已知且接受**的近似；v0.3 若要更平滑会换成令牌桶，代价是多存一个时间戳字段

## 代价

- 固定窗口的边界突刺（见上）
- 多实例下所有节点竞争同一个 key，热点租户会有 Redis 单键压力。v0.3 若出现热点，按租户分片到多个 key 再加总
- 没有"预付费额度/配额"这类业务概念，只有速率
