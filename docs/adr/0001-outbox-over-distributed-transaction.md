# ADR-0001：用事务 Outbox，而不是分布式事务

- 状态：已采纳（v0.1）
- 日期：2026-10-22

## 背景

接收事件需要同时完成两件事：

1. 把 `event` / `delivery` 写进 MySQL（业务事实）
2. 把"该投递了"这条工作消息发给 RabbitMQ（副作用）

这是典型的"两个系统、一个原子动作"问题。选项有三个。

## 选项

| 方案 | 做法 | 代价 |
|---|---|---|
| A. 先写库、再发 MQ | 简单 | **写库成功、发 MQ 失败＝事件永久丢失**，且无人知道 |
| B. 先发 MQ、再写库 | 简单 | 消费者可能读到还不存在的数据；写库失败则投递了不存在的事件 |
| C. 两阶段提交（XA） | 数据库 + broker 分布式事务 | 运维复杂度高、性能差、RabbitMQ 的 XA 支持在实践中很脆弱；云托管 MySQL 常不支持 |
| **D. 事务 Outbox** | 业务行与 outbox 行同一事务落库；独立 relay 把 outbox 转成消息 | 多一张表、多一个进程；需要处理 relay 崩溃 |

## 决定

选择 **D**。

`outbox` 与 `event` / `delivery` 在**同一个本地事务**中提交。本地事务一旦提交，工作意图就是持久化的，MQ 是否可达不再影响数据正确性。relay 进程读取 outbox 并发布，发布成功（broker confirm）后才标记 `PUBLISHED`。

## 代价与已知问题

1. **引入 at-least-once**：relay 可能在"broker 已确认"和"标记 PUBLISHED"之间崩溃，恢复后会重发。**这是这个方案不可消除的属性**，见 ADR-0002。
2. **多一次延迟**：事件提交到真正投递之间多了一段 relay 轮询间隔（默认 300ms 级）。
3. **多一张表要清理**：`outbox` 会持续增长，v0.2 需要加保留策略（按 `published_at` 归档）。
4. **relay 自身要防重复领取**：用 `SELECT ... FOR UPDATE SKIP LOCKED`，否则多实例会重复发同一批。

## 为什么不选 C

XA 在"单库 + 单 broker"的小规模场景里看着能用，但：跨系统事务会引入全局锁和协调者单点；MySQL 8.4 的 XA 在高并发下性能损失明显；而且它并不能解决"接收方那边"的不确定性——真正难的部分一点没减少。用可观测、可重放的方式换取强一致，比用 XA 换取"看起来强一致"更划算。

## 如何验证这个决策是对的

- `EventIngestIT`：并发重复提交只产生一个事件，且 outbox 行与 delivery 行数量一致
- 故障演练 1（v0.2）：在 relay 已 confirm、未标记时 `kill -9`，重启后消息重复但 delivery 状态机不被破坏
