> 约定：**S** ≈ 半天，**M** ≈ 1–3 天，**L** ≈ 1–2 周。每个任务都写了「验收」，没写验收的任务不算任务。

### A. 生产就绪债（先做这批）

#### A1. `delivery_attempt` 保留策略　`P1 / S`　✅ **已完成**

**为什么**：`outbox` 有 7 天清理，attempt 没有。上线三个月后这张表会成为最大的表，而它只在排查时用。

**做什么**
- `V3__delivery_attempt_retention.sql`：`ALTER TABLE delivery_attempt ADD KEY idx_attempt_started (started_at)`
- 新建 `worker/DeliveryAttemptRetention.java`，形状**照抄** [`relay/OutboxRetention.java`](../src/main/java/dev/hookflow/relay/OutboxRetention.java)：`@Scheduled` + 批量 `DELETE ... WHERE started_at < NOW(3) - INTERVAL ? DAY LIMIT ?`
- 配置：`hookflow.retention.attempt-days`（默认 7，`0` 关闭）
- 指标：`hookflow.attempt.pruned`

**坑（重要）**：不要删还在 `IN_PROGRESS` 的 attempt。`DeliveryProcessor.settle` 调 `attemptMapper.finish(...)` 时带 `status='IN_PROGRESS'` 条件，行被删掉会**静默更新 0 行**。保留期 ≥ `lease.ttl-seconds` + 1 天即可，但要在测试里钉住这个前提。

**验收**
- `AttemptRetentionIT`：造 30 天前的 attempt + 1 条 `IN_PROGRESS` 的 → 跑一次清理 → 旧的没了、`IN_PROGRESS` 的还在
- 配置 `0` 时完全不动表
- [operations.md §3](operations.md) 增加该指标与阈值

**结果（v0.4）**
- 迁移 `V3`：只加 `idx_attempt_started`（时间范围 DELETE 用不上 `uk_attempt_delivery_no`，没有它会变成每批全表扫）
- `worker/DeliveryAttemptRetention`：`@Profile({"worker","all"})`，每批 5 000 行、每次最多 20 批；`status <> 'IN_PROGRESS'` **写死在 SQL 里**，Java 侧无法绕过
- 配置 `hookflow.retention.attempt-days`（默认 7，`0` 关闭）+ `hookflow.retention.interval-ms`（默认 1h）
- 指标 `hookflow.attempt.pruned`；[operations.md §3](operations.md) 阈值表 + §6 数据保留一节重写（含 `IN_PROGRESS` 例外的原因与核对清单）
- 测试：`AttemptRetentionIT`（真实 MySQL：30 天前的 finished 被删、`IN_PROGRESS` 的无论多老都保留、`V3` 索引存在、清理后 settle 仍能命中行）；`DeliveryAttemptRetentionTest`（`0` 不发任何 SQL、批次循环有界、**保留期 ≥ lease TTL + 1 天的前提直接读 `application.yml` 验证**）

#### A2. 批量提交 `POST /v1/events/batch`　`P1 / M`　✅ **已完成**

**为什么**：ingest 的成本是「每事件一个事务 + ≈7 条语句 + 1 次 fsync」。批量能把这条曲线压平，是提升容量最直接的手段（比加机器便宜）。

**做什么**
- `api/EventController` 增加 `POST /v1/events/batch`，请求体 `{"events":[{"eventType","payload","idempotencyKey"}, ...]}`，上限 500 条
- `EventIngestService.ingestBatch(tenantId, List<Item>)`：**一个事务**内 `INSERT ... VALUES (...),(...)` 批量写 event / delivery / outbox（MyBatis `<foreach>`）
- 部分重复（幂等键已存在）**不报错**：返回逐条结果 `[{index, eventId, deliveryCount, replay:true|false}]`
- 整批失败（如 DB 不可用）返回 503，语义与单条一致
- 限流与背压按**条数**计（不是按请求数），否则批量接口会绕过降载

**验收**
- `BatchIngestIT`：20 条里夹 3 条已存在的幂等键 → 全部返回正确 eventId，事件总数不重复
- 压测：同机 `events/s` 相对单条路径有可测提升，**且单条路径 p99 不退化**（用 `scripts/bench.ps1`，结果进 `docs/perf/`）
- `docs/api.md` 增加该接口与错误码
- 文档里明确「吞吐提升来自减少事务与往返次数，不是来自并发」

**结果（v0.4）**
- 一个事务、**与 N 无关的固定几条语句**：`INSERT event`（多行）→ 按幂等键读回 id → 一次 endpoint 列表查询 → `INSERT delivery`（多行）→ 按 `event_id` 读回 id → `INSERT outbox`（多行）。读回是必须的：MyBatis + 不可变 record 拿不到多行 INSERT 的自增 id
- 常量 `EventController.MAX_BATCH_EVENTS = 500`；超限**整批 400**，不截断
- 部分重复：一批先按幂等键一次 `IN` 查出已存在的，已存在的直接标 `replay`；同批内重复的键解析到第一次出现。并发撞上时的处理与单条一致——事务回滚、重读赢家、最多 3 次，最后一次仍读不到才抛（500）
- 限流 `TenantRateLimiter.acquire(..., permits)` 用 `INCRBY`，按事件数消耗配额；降载 `BacklogGate.check(tenantId, incoming)` 按「当前积压 + N」判断
- 整批未提交（DB 不可用）→ `503` `DEPENDENCY_UNAVAILABLE`：一个事务，一条都没提交，原样重试安全
- [api.md](api.md) 新增接口、状态码、字段表、「按条计」对照表，并明确「提升来自减少事务与往返，不是并发」
- 测试：`BatchIngestIT`（真实 HTTP：20 条夹 3 条已存在 → 20 个正确 id、事件/投递都不重复；整批重放 → 200 且 id 不变；批内重复键 → 一个事件；501 条 → 400）；`TenantRateLimiterTest`（配额按条数）；`BacklogGateTest`（批量按「积压 + N」判断）
- 压测（同机、同一天、改造前后各两次单条对照）：同一到达率 **450 events/s** 下，单条路径开环 p50 / p99 = **1.10 s / 2.31 s**，批量 20 条 = **42.7 ms / 69.5 ms**；批量在 900 events/s 仍 100% 接受（p99 1.39 s）。单条路径的 p99 对照**未测出差异**：四次 300 events/s 运行的 p99 散布 64–289 ms，大于任何可能的改动效应（见 [performance.md §14.3](performance.md)）
- 原始输出：[`docs/perf/2026-10-23-batch/`](perf/2026-10-23-batch/)（含 baseline 的两次对照，以及每个目录的说明）；方法、两个测量坑与「没有证明什么」见 [performance.md §14](performance.md)
- 设计取舍（为什么一个事务、为什么每条自己的幂等键、为什么不截断、为什么读回 id）写成 [ADR-0013](adr/0013-batch-ingest.md)

**缺的是另一半**：批量把「每事件一次事务 + 一次 fsync」压成 1/20 之后，

**做什么**

- **改结论**：§3 的区间与 §4 的「先加谁」按新数据改写，换掉「D 或 E 在 350/s 附近咬合，具体未测」那句

**验收**：一张「批量前后 × 下游速率」表 + **一句明确的「新瓶颈是 X」**（X 必须是指标名）+ capacity.md
的 §2/§3/§4 不再与 §14 矛盾。

**结果（v0.4）**

- `scripts/bench.ps1` 加了三个参数，都是为了让"一次快照"变成"一条曲线"：`-SampleSeconds 5`
  （同时采 Micrometer / MySQL 行数 / broker `rabbitmqctl`，写 `series.csv` 与折算好速率的 `downstream.txt`）、
  `-TailSeconds 20`（负载停止后继续采，得到涨/平/**落**三段）、`-StatementDigest`（跑前清空、跑后导出
  `statements.txt`，即 B3 要的那张分解表）。三个参数都进 `meta.txt`，可复现。
- 三次运行（单条 450 / 批量 20 450 / 批量 20 900，各 10 s 预热 + 60 s 负载 + 20 s 观察）：
  出口速率 **30.2 / 41.5 / 39.3 events/s**；积压增长严格等于「入口 − 出口」（421 / 398 / 820 行每秒）；
  broker `messages_ready` 恒 0、`unacked` ≤3、消费者 8 个（**worker 闲置**）；
  `hikaricp_connections_pending` 批量下 0、单条下开局 36；锁冲突 0；`publish_rejected` 0。
- **新瓶颈是 `hookflow_outbox_published_total`**：41.5 events/s，与入口 450 还是 900 无关。
  每行 24 ms 拆成 **12.4 ms**（`UPDATE outbox ... WHERE id=?` 单行提交，即一次 fsync）+
  **≈11 ms**（`convertAndSend` + publisher confirm 往返）。所以只批一半的天花板是 80–90/s，两半都要批（[§16](performance.md)）。
- 结论落点：[performance.md §15](performance.md)（方法、表、积压堆在哪、修正了 §1 的哪个说法、没证明什么）、
  [capacity.md](capacity.md) §1–§6 全部重算、原始输出 [`docs/perf/2026-10-23-downstream/`](perf/2026-10-23-downstream/)。
- **B0 分叉的判定：落在第一行（relay 是瓶颈）→ 做 B4，B3 的分解已在同一次运行里拿到。**

**预判（写下来是为了让它被推翻）**：入口不再是瓶颈后，下一个是**relay 的逐条同步 confirm**
（[`DeliveryPublisher`](../src/main/java/dev/hookflow/messaging/DeliveryPublisher.java)：每条消息一次网络往返，
理论上限约 1 000/s）。如果排空速率明显低于入口速率、积压 60s 内单调上涨，那就是它。

#### B0 的分叉：按观察选下一步（不要按编号顺序做）

| B0 的观察 | 结论 | 下一步 |
|---|---|---|
| `outbox.published` 速率封顶（≈1 000/s）不再涨，worker 闲置，积压堆在 MySQL | **relay 是瓶颈** | **B4 relay 批量发布**；先用 B3 看耗时在调用往返还是语句 |
| 排空速率跟得上入口，但 `hikaricp_connections_pending > 0` 或语句级显示某条 `INSERT` 占大头 | **DB 仍是瓶颈**，形态变了 | **B3 语句级拆解** → 再决定连接池 / group commit / 批量插入 |
| worker 忙、接收方延迟主导（重试上升、worker 线程打满） | **worker / 接收方是瓶颈** | 不是加机器能解决的：梳理 `endpoint.max_concurrency` 默认值 + 在 capacity.md 写清「容量 = 并发 ÷ 接收方延迟」 |
| 三样都不满，但 p99 抖动大 | 锁竞争或 GC | JFR + `SHOW ENGINE INNODB STATUS` 看锁等待；此时才谈 G1 / 参数 |

#### B3. ingest 语句级拆解　`P2 / S`　✅ **已完成**（与 B0 同一次运行采集）

**为什么**：[performance.md §5.5](performance.md) 只测到「一次 ingest 16–23ms」，但没拆开是哪几条语句。文档里现在写的是「没测到，不猜」。

**做什么**：`SELECT * FROM performance_schema.events_statements_summary_by_digest WHERE schema_name='hookflow' ORDER BY SUM_TIMER_WAIT DESC`，按 digest 聚合出每条语句的耗时与次数占比；写进 performance 报告新增一节。

**验收**：那 16–23ms 有了分解表，且「没测到的部分不猜」那段被删掉或缩小

**结果（v0.4）**

- 工具化而不是手工查询：`bench.ps1 -StatementDigest` 在应用启动前 `TRUNCATE performance_schema.events_statements_summary_by_digest`，
  跑完把 top-40 导出成 `statements.txt`（列：次数、总秒、平均毫秒、平均影响行数、锁时间、digest）。窗口 = 本次运行，
  所以每次运行都能拿到自己的分解表，不必事后再猜是"哪一次"。
- 分解结果见 [performance.md §15.4](performance.md)：批量入口下一次 ingest 批事务 ≈14.5 ms，其中
  `INSERT event/outbox/delivery` 三条多行插入合计 ≈1.9 ms，**剩下的 12.6 ms 是那次提交（fsync）**；
  relay 的每行 `UPDATE outbox` 是 12.4 ms。也就是说 §5.5 当年那句"16–23 ms 里没测到的部分"
  现在是：**提交占绝对多数，语句本身只占 10%–15%**。
- [performance.md §5.5](performance.md) 的「没测到的部分，不猜」已改写为指向 §15.4 的结论，并保留"语句之间往返"
  这一项仍然没有单独计时的事实。

#### B4. relay 批量发布（可选）　`P2 / M`　✅ **已完成**

**做什么**：`DeliveryPublisher` 目前逐条同步等 confirm。改成「一次发布 N 条、批量等 confirm」或异步确认窗口；`OutboxRelay.publishBatch` 相应改造。

**验收**：`hookflow.outbox.published` 的速率上限提升有实测；失败回退路径（`releaseBack`）不被破坏，`BrokerOutageIT` 仍绿

**结果（v0.4）**

- `DeliveryPublisher.publishAll`：先全部发出、再按顺序等确认，**整批一个 10 s 截止时间**（不是每条一个，
  否则一 tick 最坏能挂 20×50×10 s）；返回逐条 `ACKED / NACKED / FAILED`。
- `OutboxRelay.publishBatch`：ack 的 id 走新增的 `markPublishedBatch`（**一条 UPDATE**），
  nack/未确认的走 `releaseBackBatch`（也是一条 UPDATE），计数分别进 `outbox.published` / `publish_rejected` / `publish_failed`。
  **没有 ack 绝不标记 PUBLISHED**；任何一条失败就停这一 tick（保持 v0.3 的"broker 不健康就别空转"）。
- 单条 `publish(...)` 保留：`OutboxCrashWindowIT` 用它构造"已确认但没标记"的崩溃窗口。
- 实测（同一台机器、同样的到达率与线程数，只改代码）：relay **41.5 → 400–466 events/s（≈10.7×）**；
  450 入口下 outbox 积压从"每秒涨 400 行"变成"60 秒里 61 → 829 行"；900 入口下发布仍是 390–460/s，
  所以 **relay 的新上限 ≈ 440/s**。见 [performance.md §16](performance.md)、原始输出
  [`docs/perf/2026-10-23-relay-batch/`](perf/2026-10-23-relay-batch/)。
- **瓶颈按分叉表往下走了一格**：worker 的交付速率 135–190/s 成为最紧的一项（`messages_ready` 一路涨到
  20 000 的队列上限、`unacked` 钉在 `8 × 8 = 64`）。这不是新问题，是 B4 之后**下一步该做的事**（见 capacity.md §4）。
- 失败路径在真实过载下也走了一遍：队列到上限后 nack ≈175/s，行全部回到 NEW（结束时 `NEW`=731、`PUBLISHING`=50），
  负载停下后自动恢复发布——不需要人工干预。
- 代码 + 测试：`DeliveryPublisherTest`（4 条：broker 不可达全 FAILED / 全 ack / nack / 确认永不到达）、
  `OutboxRelayPublishBatchTest`（5 条：一批一次 UPDATE / 混合 nack / 未确认不标记 / 坏 payload 跳过 / 空批不碰 broker）；
  `BrokerOutageIT` 仍绿。设计取舍写成 [ADR-0014](adr/0014-batched-relay-publish.md)。
