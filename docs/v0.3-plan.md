# v0.3 计划：真实性能数据

- 状态：未开始
- 前置：v0.2.0 已完成并打 tag（67 个测试全绿，三次真实演练通过）

## 1. 为什么是这五件事

v0.2 之后，项目能回答"崩溃了会怎样""依赖挂了会怎样"。**它还不能回答"能扛多少"**——而这恰恰是"高并发"这个词唯一诚实的含义。

v0.3 的目标不是把 QPS 数字刷高，而是**用可复现的测量方法说清瓶颈在哪、扩容先加谁**。所以顺序是：先解决会限制规模的隔离问题，再测，再解释。

## 2. 范围

### 2.1 多租户公平调度（优先级最高）

**问题**：现在所有 delivery 进同一个队列，一个大租户的积压会把 worker 线程池占满，小租户的事件被饿死。这是真实的"多租户"缺陷，不是性能问题。

**做法**：

- 按 `tenant_id` 分片到 N 个队列（`hookflow.delivery.{shard}`），或单一队列 + 按租户限速消费
- 加权轮询：给每个租户一个权重，调度时保证每个租户在任意窗口内至少被服务一次
- 每个 endpoint 的并发上限（`endpoint.max_concurrency` 已存在于设计稿，v0.2 未实现）

**验收**：

- 一个租户灌入 10000 个事件的同时，另一个租户提交 10 个事件，后者 p99 延迟不显著上升
- 测试用 `FairnessIT` 量化：写出"饥饿比率"，改前改后对比

**风险**：分片队列会引入"跨分片无序"，需在接受范围内；先做加权轮询（单队列）可能已足够，需实测比较。

### 2.2 背压与降载

**问题**：outbox 无长度上限、队列无上限、没有拒绝策略。突发流量会把内存和 MySQL 打满，最后是雪崩而不是降级。

**做法**：

- **outbox 高水位**：超过阈值时，`POST /v1/events` 返回 429/503 而不是无限写入
- **队列长度上限** + 明确的拒绝语义
- **worker 有界线程池**：线程池满时的拒绝策略做成可配置并实测代价
- 三种策略的取舍写进文档：阻塞生产者 / 拒绝并 429 / 丢弃低优先级

**验收**：

- 压测中把到达率提到容量 3 倍，观察：是平稳降级（429 比例上升、延迟不爆炸）还是雪崩
- `max_in_flight` / `outbox_backlog` 指标能提前预警

### 2.3 严格的延迟测量 + JVM 证据

**关键细节：不用朴素压测。**

k6/ab 默认是"闭环"压测，在系统过载时会产生 **coordinated omission**，把 p99 严重低估。用 **wrk2 的 `--rate`**（开环、按目标速率发压）做修正测量，并解释两个工具为什么给出不同的数字——这个解释本身就是深度。

**采集**：

- `-Xlog:gc*` 的 GC 日志 + 停顿统计
- **JFR** 抓分配热点：谁在制造垃圾
- **async-profiler 火焰图**：CPU 时间花在哪
- G1 调参前后对比（`MaxGCPauseMillis`、`InitiatingHeapOccupancyPercent`）

**验收**：一份报告，必须包含

- 机器规格、Docker 配置、payload 大小、并发数、持续时间
- 吞吐 + p50/p95/p99 + 错误率 + 队列积压
- **瓶颈判定**：DB 写？网络？lease 续约？火焰图指向哪里
- **优化前后对比**：改了什么、效果多少、代价是什么
- 原始命令与原始输出（可复现）

**红线**：测不出来就不写数字。README 里继续不出现任何未测的 QPS。

### 2.4 容量模型

`docs/capacity.md`：给定 4C8G 单机、payload 2KB、目标 p99 < 500ms，能支撑多少 TPS；瓶颈在 DB 写还是网络；扩容时先加 api / relay / worker 中的哪个，各自的边际收益。

**这是把"我压过测"变成"我知道为什么"的关键一步。**

### 2.5 OpenTelemetry trace 贯通

`api → outbox → relay → MQ(headers) → worker → receiver`，一个 traceId 串起来。

**设计要点**：

- trace 上下文序列化进 `DeliveryMessage`（或 AMQP headers），worker 侧恢复
- 出站请求带 `traceparent`，接收方可以据此关联
- 本地用 Jaeger/Tempo 起一个 collector，README 给一键命令

**验收**：一条慢投递能在 Jaeger 里看到耗时分布在哪一段（入队、等待、HTTP）。

**依赖**：`micrometer-tracing-bridge-otel` + `opentelemetry-exporter-otlp`。注意 Boot 4.1 的版本管理，可能需显式指定。

## 3. 明确不做

- 微服务拆分、Kubernetes 生产化（v0.4 之后，且需真实需求）
- 第二套 MQ 实现（v0.4 的传输层 SPI）
- 管理 UI、SDK（v0.4）
- 分库分表：没有数据量支撑，做了就是装饰

## 4. 已知技术债（承接 v0.2）

| 债务 | 优先级 |
|---|---|
| 无背压 / 无租户公平调度 | **v0.3 解决**（2.1 / 2.2） |
| 无压测数据 | **v0.3 解决**（2.3 / 2.4） |
| 无分布式 trace | **v0.3 解决**（2.5） |

| 顺序投递未实现 | 明确列为「不保证」，不打算做 |

## 5. 环境与常用命令

| 事项 | 命令 / 说明 |
|---|---|
| 依赖 | `docker compose up -d`；本机 3306 被占用，用 `DB_PUBLISH_PORT=13306`，并设 `DB_PORT=13306` |
| 构建 | `.\mvnw.cmd -B -DskipTests package`（Maven Wrapper 3.9.14 已就绪） |
| 单元测试 | `.\mvnw.cmd test`（47 个，秒级，无需 Docker） |
| 全量 | `.\mvnw.cmd verify`（67 个，含 Testcontainers；约 2–4 分钟） |
| 故障演练 | `.\scripts\drill.ps1 -DbPort 13306`（约 3 分钟） |
| 演示 | `docker compose up -d` → `.\mvnw.cmd spring-boot:run` → `java -cp target\classes dev.hookflow.tools.MockReceiver 9099` → `.\scripts\demo.ps1` |
| 角色端口 | api 8080 / relay 8081 / worker 8082（可用 `RELAY_PORT`/`WORKER_PORT` 覆盖） |

### 环境注意事项（都是实际踩过的）

1. **本机 3306 被已有 MySQL 占用**，compose 里用 `DB_PUBLISH_PORT` 换宿主端口。
2. **PowerShell 5.1 读无 BOM 的 .ps1 会按 ANSI 解析**，含中文的脚本必须存成 UTF-8 with BOM（`demo.ps1` 已处理）。`drill.ps1` 刻意全英文，避免这个问题。
3. **`Start-Process` 在本机会失败**：环境里同时存在 `HTTP_PROXY` 和 `http_proxy`，PS 构建子进程环境时报 "item already added"。`drill.ps1` 改用 `Win32_Process.Create` + 临时 .bat 规避，且**通过 .bat 显式 set 环境变量**（WMI 启动的子进程不继承当前 PS 会话的环境）。
4. **Toxiproxy 不可用**，原因与替代方案见 [ADR-0008](adr/0008-fault-injection-tooling.md)，不要再浪费时间重试。
5. **多构造器的 Bean 必须显式 `@Autowired`**（`SecretCipher`、`EgressGuard` 都踩过），否则 Spring 启动失败。
6. **Boot 4 的 Flyway 自动配置在 `spring-boot-starter-flyway`**，只加 `flyway-core` 会静默不执行迁移。
7. 时间运算一律在 MySQL 内完成（`NOW(3) + INTERVAL`），不要用 Java 算绝对时间（见 [failures/0002](failures/0002-two-clocks.md)）。

## 6. 完成标准

v0.3 结束时应当能回答这四个问题，且每个答案都有文档和原始数据：

1. 单机 4C8G 能稳定支撑多少事件/秒？瓶颈在哪一类资源？
2. 大租户刷流量时，小租户的延迟会受影响吗？数据是多少？
3. 过载 3 倍时系统是降级还是雪崩？降级的形态是什么？
4. 一条投递慢，是慢在排队、慢在 relay、还是慢在接收方？trace 能看到吗？
