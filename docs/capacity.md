# 容量模型：4C8G 单机能扛多少，先加谁

- 版本：v0.4（B0 再基线 → B4 relay 批量发布 → B5 worker 并发）
- 依据：全部系数来自 [performance.md](performance.md) 的实测（本机 i5-14600K 14C/20T，见该文 §2）
- **诚实声明**：本文的公式是实测的，代入本机测出的系数；**没有一台 4C8G 的机器可以实测**，所以 4C8G 的结论是
  "区间 + 判据"，不是"我跑过"。凡是没测的地方都标了「未测」。
- **这一版改了三个数**（v0.3 的版本错了不止一处，错在把"入口能接多少"当成了"平台能送多少"）：
  持续吞吐从 v0.3 声称的 300–350 events/s 修正为 **41 events/s（B0 前）→ 264 events/s（现在）**；
  瓶颈从"DB 提交"变成"relay 逐条发布"（B0），再变成"worker 每次投递两次提交"（B4）；
  worker 一格的旋钮也量了（B5）：**只有并发有用，prefetch 没用**。

---

## 1. 一条投递要花什么

一个事件从 `POST /v1/events` 到一个 2xx 的完整成本，按实测拆开（批量入口，20 条/请求）：

| 阶段 | 每次事件的数量 | 实测单位成本 | 证据 |
|---|---|---|---|
| ingest 事务（批量） | 1/20 个事务 / 固定约 6 条语句 | 批事务 ≈14.5 ms 服务端、其中语句 0.3–1.1 ms/条 | [§15.4](performance.md#154-新瓶颈是-hookflow_outbox_published_total每行-24-ms-花在两处) |
| 其中 DB 连接占用 | — | `hikaricp_connections_pending` 批量下恒 0；单条入口下 36–42 | §15.2、[§16.4](performance.md#164-单条入口那次池被-ingest-占满不是-b4-的锅) |
| **relay 发布（B0 前）** | 每事件 1 次 confirm + 1 次单行 UPDATE 提交 | **24 ms**（12.4 + 11）→ 上限 **41 events/s** | §15.4 |
| **relay 发布（B4 后）** | 每批 46 行：1 次 confirm 窗口 + 1 次批量 UPDATE | 每行 0.48 ms + 每批 ≈100 ms 固定成本 → **400–466 events/s** | [§16.2](performance.md#162-为什么-relay-卡在-440s-而不是几千) |
| **worker 认领 + 结算** | 每投递 2 个事务（claim + settle），各 1 次提交 | 提交 19.0–19.4 ms（16 并发时）、语句合计 ≈1.5 ms → **8 并发 158/s，16 并发 273–296/s** | [§18](performance.md#18-worker-那一格并发是唯一的旋钮prefetch-不是) |
| worker 出站 HTTP | 1 次 POST | 本组接收方 ≈2 ms（故障演练里 200 ms–3 s） | §7 / `ReceiverFaultIT` |
| GC | — | 0.25–0.40% wall time | [§5.1](performance.md#51-gc-不是每个场景都一样) |
| CPU | — | ≈0.04 核（等待为主） | [§5.3](performance.md#53-jfr进程基本在等-io) |

**关键结论没变：成本几乎全是 I/O 往返与提交，不是 CPU。** 所以按 CPU 核数做线性外推（"14C → 4C 就是 3.5 分之一"）是错的。
变的是**哪一段最贵**：v0.3 认为是一次 ingest 一个事务，B0 证明是 relay 的逐条发布，B4 之后是 worker 的两次提交。

## 2. 容量公式（五个约束取最小值）

```
TPS_max = min(
    A: ingest_threads / ingest_service_time,        # API 线程与批事务的串行度
    B: db_connections / db_hold_time,               # 连接池与并发需求（不是提交速率）
    C: redo_commit_rate,                            # 提交持久化：现在是「每 20 个事件 1 次」
    D: relay_publishes_per_second,                  # relay 的批发布节拍
    E: worker_threads / per_delivery_cost          # worker 并发 ÷ 每次投递的成本（两次提交 + 一次 HTTP）
) × (1 - headroom)                                  # 留 30% 余量给突发与重试
```

各约束在本机测到的值（**B0 前 → B4 后**）：

| 约束 | 实测 | 说明 |
|---|---|---|
| A 入口线程 | 批量：200 线程 / 14.5 ms ≈ 13 800 批/s = **276 000 events/s**（不构成约束）；单条：450 events/s 时 9–40 个连接在途 | 入口从来不是瓶颈，池与下游才是 |
| B 连接 | 批量下 `pending` 恒 0；**单条入口下 36–42** → 16 个连接对"单条 + 活跃下游"不够 | B 的约束是**并发需求**，不是提交速率 |
| C 提交 | 一次提交 12.6–16.4 ms；批量下每事件 1/20 → `16 / 0.0126 ≈ 1 270` 提交/s ≈ **25 000 events/s** | 批量之后 C 不再是约束（这正是 A2 换来的） |
| D relay | **41 events/s → 400–466 events/s** | 见 [§16.1](performance.md#161-同一张表加了-b4-这一行)；batching confirm 与 batching UPDATE 各贡献一半 |
| E worker | `16 并发 / (2 × 19.4 ms + 2 ms) ≈ 390/s` 的理论值；实测 **158/s（8 并发）、273–296/s（16 并发）**，32 并发时 relay 先满（≥361/s） | 见 [§18](performance.md#18-worker-那一格并发是唯一的旋钮prefetch-不是)：并发几乎线性，但每消费者的效率从 19.7 掉到 17.1/s；`DB_POOL_SIZE=16` 在 16 并发时刚好卡住 |

代入本机（300 events/s 批量入口）：

- **B0 前**：`min(276 000, 很多, 25 000, 41, 240) × 0.7 ≈ 29/s`，实测 41/s（41 是"上限"，×0.7 是留给突发与重试的余量）
- **B4 后（8 消费者，2→8 爬坡）**：`min(276 000, 很多, 25 000, 440, 190) × 0.7 ≈ 130/s`，实测整次 152/s
- **现在（B5：8→16 并发）**：`min(276 000, 很多, 25 000, 440, 283) × 0.7 ≈ 198/s`，实测整次 **264/s**、稳态 283/s

**这三行就是本文的全部结论**：v0.3 的 300–350/s 是"入口在接受"的数字，不是"平台在送"的数字；
把它当容量用，会得到一个必然堆积的系统（[§15.5](performance.md#155-这一节修正了-1-的一个说法)）。
而持续吞吐从 41 → 264/s 是两次改动换来的：relay 批量发布（10.7×）与 worker 并发翻倍（+74%）。

## 3. 4C8G 的答案

把上面各约束换成 4C8G 上应有的值（这一步是模型，不是实测）：

| 约束 | 4C8G 的估计 | 为什么 |
|---|---|---|
| A（线程/批事务） | 不构成约束 | 成本是 I/O 等待，CPU 采样只有 0.04 核 |
| B（连接） | **更紧**：4 核上 MySQL 与 Java 抢同一块盘，单次连接占用更长 | 同机部署时 16 个连接比本机更容易被占满 |
| C（提交） | 批量后不构成约束 | 每 20 个事件 1 次提交 |
| D（relay） | 与本机同量级或略低：单线程，成本是 confirm 往返 + 每批一次提交 | **未测**。本机 400–466/s，4C8G 估计 200–400/s |
| E（worker） | `并发 / (2 × 提交延迟 + HTTP)`；提交延迟在 4C8G 上更接近 20–30 ms → 16 并发约 **150–250/s**；并发调到 32 之前要先确认 relay 追得上（本机在 32 时先到顶） | 纯并发 ÷ 成本，与核数关系不大；**未测** |

**结论（区间，不是点估计）**：

> 4C8G 同机部署（api+relay+worker 一个进程、MySQL 同机 Docker）、payload 2KB、接收方延迟 ≈5ms、目标 **p99 < 500ms**：
> **持续吞吐 ≈ 150–250 events/s**（B5 之后：worker 16 并发、relay 400+/s），入口能接 150–300 events/s（批量）——两者不是一回事。
> 下限对应"提交 30 ms + 池 16"，上限对应"提交 20 ms + 池 24–32"。
> **现在最紧的约束是 E（worker 的两次提交），其次是 D（relay 每批两次提交），C（提交持久化）已经不再是问题。**
> 若接收方延迟升到 200ms，**E 更早成为约束**：`16 / 0.2 = 80 events/s`，此时容量与 DB、CPU 都无关。

**缓冲与水位线的定量依据**：B4 之后 outbox 可以真的当缓冲用（relay 追得上，积压不涨），
但 broker 队列有 20 000 行的硬上限——B4 的第一次压测就撞到了它（[§16.3](performance.md#163-队列上限被撞到之后发生了什么失败路径的真实证据)）。
所以"允许的等待时间 × 排空速率"这个公式里的"排空速率"要取 **worker 的速率**（现在 264–283/s），不是 relay 的：
租户水位线 10 000 行 ÷ 265/s ≈ 38 s 的额定等待——比 ADR-0010 当初按 300/s 估的 33 s 略长，量级一致，
但**当时用来算它的 300/s 恰好接近今天的真实值，纯属巧合：B4 之前真实排空只有 41/s，那个 300/s 是错的**。

## 4. 扩容先加谁：按"当前咬合的是哪个约束"决策

不要问"先加哪个组件"，要问"现在哪个约束在咬合"。下表每一行都对应一个**能直接看到的指标**：

| 现象（一眼能看出来） | 咬合的约束 | 先加谁 | 边际收益（实测） |
|---|---|---|---|
| `messages_ready` 持续上涨 + `unacked` 钉在 `concurrency × prefetch` | **E worker** | 调 `MQ_CONCURRENCY` / `MQ_MAX_CONCURRENCY`（**prefetch 无关，别调**），池跟着加；再往上要合并 claim+settle 两次提交 | 8→16 = 158 → 273/s（+73%）；16 并发 + 池 32 = 296/s；32 并发无收益（relay 先满）；新默认（8→16）实测整次 264/s（[§18](performance.md#18-worker-那一格并发是唯一的旋钮prefetch-不是)） |
| `hookflow_outbox_publish_rejected_total > 0` | 队列上限（护栏，不是约束） | 不是加机器：说明 worker 追不上 relay，积压回 MySQL 是**设计行为** | B4 压测中实测 175/s 的 nack，行全部回到 NEW |
| outbox 积压涨而 broker 队列空 | **D relay** | 批量发布（B4，已做）；再往上要动"每批两次提交" | 41 → 400–466/s（10.7×） |
| `hikaricp_connections_pending > 0` | **B 连接** | `DB_POOL_SIZE`（16 并发时确实会到 3）；若同时是单条入口，先改成批量入口（提交数 1/20） | 单条入口实测 pending 36–42、开环 p50 7.7 s；16 并发 + 池 16 时 pending 3，池 32 后 0 且 +8% |
| p99 随 ingest 速率上升、`pending=0`、CPU 空闲 | C 提交（**v0.3 的结论，现在不成立**） | 批量入口已经把每事件提交降到 1/20；单条入口仍受此限 | fsync=2 时 p99 −39%（v0.3） |
| CPU 饱和（本机不是） | A | 加 api 实例 | 单机实测用不到 |

三条容易踩的坑（第一条是 B0 学到的，第二条是 B5 学到的）：

1. **"入口能接"不等于"平台能送"。** 差一个数量级的两个数字曾经被写在同一张表里（300–350 vs 41）。
   看到吞吐数字先问一句：它是**接受的**还是**完成投递的**？
2. **调参前先确认"这一格还在瓶颈上"。** `MQ_PREFETCH` 从 8 调到 32 对吞吐**没有任何作用**（158 vs 148、273 vs 278），
   只是把 `unacked` 从 64 抬到 512；而 32 并发在一台 relay 只有 440/s 的机器上也没有收益。
3. **接收方慢的时候，是接收方在决定你的容量**：`16 / 0.2 = 80/s`。此时唯一的扩容方式是限制该 endpoint 的
   `max_concurrency`，别让它把整个租户拖住（v0.3 已实现），而不是加机器或加并发。

## 5. 这个模型哪里可能是错的

| 假设 | 风险 | 怎么证伪 | 现状 |
|---|---|---|---|
| ~~ingest 成本主要是提交 fsync~~ | v0.3 的假设 | 语句级摘要 | **已证伪**（[§15.4](performance.md#154-新瓶颈是-hookflow_outbox_published_total每行-24-ms-花在两处)）：批量入口下 ingest 只占模型里的极小项 |
| ~~relay 不是约束~~ | v0.3 的假设 | 对比 `hookflow_outbox_published_total` 与 worker 完成速率 | **已证伪**：41 events/s，是 B0 时最紧的一项 |
| ~~worker 不是约束~~ | B0 时的观察（worker 闲置） | 同上 | **已证伪（B4 之后）**：它是现在最紧的一项，8 并发 158/s、16 并发 273–296/s |
| ~~prefetch 越大 worker 越快~~ | 直觉 / 消息队列常见建议 | 并发固定、prefetch 8 vs 32 | **已证伪**（[§18](performance.md#18-worker-那一格并发是唯一的旋钮prefetch-不是)）：148 vs 158、278 vs 273，都在噪声内 |
| worker 并发可以一直线性加到 32 | 8→16 是 1.73× | 32 并发 + 池 32 | **部分证伪**：32 并发时 relay 先满（队列峰值 0），worker 只测到下界 ≥361/s |
| "每批一次提交"的固定成本可以忽略 | relay 的 440/s 上限由 claim + markPublished 两次提交构成 | 压测时看 `statements.txt` 的 `COMMIT` 分布 | 未拆开测；§16.2 只给了量级 |
| 队列上限 20 000 是护栏 | 它现在是**真的会被撞到**的（B4 之前永远撞不到） | 大积压下的 nack 行为 | 已复现（§16.3） |
| 4C8G 与 14C/20T 的差别主要在 I/O | 如果 MySQL 与应用分机部署，结论会明显乐观 | 需要一台 4C8G 实测 | **未测** |
| 接收方 5ms | 真实客户公网 P99 常见 200ms+ | 用 `?delay=` 复现，见 `bench.ps1 -ReceiverDelayMs` | 未测（本组 2 ms） |

**没测到的东西，本文不写数字。** 上表里带「未测」的行就是因此标出来的。

## 6. 一句话

**持续吞吐从 41 events/s 走到 264/s，用了两步：B4 把 relay 的"每行一次 confirm + 一次 UPDATE 提交"
批量化（41 → 440/s），B5 把 worker 并发从 8 提到 16（158 → 283/s）。现在最紧的是 worker 的"每次投递两次提交"，
其次是 relay 的"每批两次提交"——两者是同一件事，合并提交次数就是下一刀。**
4C8G 同机部署估计 150–250 events/s（模型）；扩容顺序由指标决定，最常见的错误是
① 在 worker 已经咬合时去加 api 实例，② 把"入口接受速率"当成"平台吞吐"，
③ 在没有确认"这一格还在瓶颈上"的时候调参数（比如把 prefetch 调大）。
