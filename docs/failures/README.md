# 故障、缺陷与演练记录索引

这个目录记录**真实发生过**的故障、缺陷，以及每一次故障演练的实测结果。

## 为什么单独建目录

大多数项目只在 commit message 里留一句 "fix bug"。但对一个主打可靠性的项目来说，**最有价值的信息是"你曾经在什么地方出错，以及你怎么证明它不会再犯"**——因为：

1. 它证明你真的跑过系统，而不只是把它写出来
2. 复盘的结构（现象 → 根因 → 修复 → 回归）本身就是工程能力的体现
3. 三个月后回看，你能记得当时的判断依据，而不是只记得"改了一行"

## 三条缺陷的共同点

三个 P1 缺陷都不是"写错了逻辑"，而是**边界没被测试碰到**：

| 缺陷 | 为什么 v0.1 全绿的测试没发现 |
|---|---|
| 0001 | 需要**真并发 + 真实 MVCC**；单线程测试和 H2 都掩盖它 |
| 0002 | 需要**JVM 与数据库时区不一致**；同进程内的测试两边时区一致 |
| 0003 | 需要**依赖真的不可用**；所有正常路径测试都不会走进那条错误分支 |
| 0007 | 需要**同时有上千行在被认领**；v0.2 的测试每次只有一两条 delivery，加锁顺序永远不冲突 |

结论：**测试通过只说明"考虑过的路径"是对的；故障注入才能说明"没考虑过的路径"不会致命。** 而 0007 补充了第三种发现方式：**把并发量提高到真实规模**——它既不是逻辑写错，也不是依赖故障，而是"小规模下看不见的调度交互"。

## 模板

新建记录时复制 [TEMPLATE.md](TEMPLATE.md)。

约定：

- 一个事件一个文件，命名 `NNNN-短标题.md`
- **只记录真实发生的**。演练标 `演练`，真实踩到的 bug 标 `缺陷`
- 不确定的地方写"未确认"，不要编造根因
- 缺陷必须有回归测试，演练必须有可重放命令
